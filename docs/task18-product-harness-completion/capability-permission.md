# Task 18.4 capability permission model

`Bot.capabilityRules` is an optional JSON array validated against the version-one rule schema (`capability`, `resource` glob, `scope`, `effect`). The executor re-reads it at every resolved tool call, including a replay of a previously approved request. A malformed policy blocks the tool instead of falling through. `deny` wins over `ask`, which wins over `allow`; scope (`bot > user > space`) and literal pattern length break ties. A deny cannot be weakened by a narrower allow. No matching rule leaves the existing approval and resource authorization path in control.

The built-in rules allow `read_file`, require a human ask for `send_email`, and deny `delete_*` against a resource identified as `production/**`. A path, resource identifier, or connector route supplies the resource; an explicit `environment=production` prefixes it. The system does not infer a production environment from arbitrary connector payloads. Deletion with an unclassified target continues through the existing approval path, so this default is **not** a universal production-data detector. Explicit Bot rules can cover additional tool names and known resource identifiers. No rule can create a connector credential, a Space membership, or a file permission.

The design places all version-one rules on a Bot while giving each rule a `space | user | bot` scope. Consequently, scope currently ranks rules within that Bot's own policy; it does not install a policy across all Bots or users in a Space. A future global policy store would need explicit subject identities and a migration. The existing AgentScope helper catalog and backend background tool bridge still enforce read-only tools, and the same Bot policy is checked when those tools execute. Write work must return to the parent Run for its normal approval and permission path.

The Prisma migration applies to a disposable PostgreSQL database. Contract/core checks, capability-rule unit tests (`capability-rules.test.ts`, `capability-permission.test.ts`), and the full TypeScript workspace check pass.

The real Web → API → Java AgentScope → Tool Bridge → executor acceptance trace is captured in `apps/web/e2e/capability-rules.spec.ts` (runs with `--runtime=agentscope`; the model is the offline emulator, but the tool request travels the real bridge and the decision happens at the production `evaluateBotToolCapability` boundary):

- "deny and malformed capability rules block the real tool boundary without approval": a persisted Bot deny rule stops `write_file` inside the real executor — the tool implementation never runs (no file exists), no `ExternalEffect` is committed, no approval Intervention is created, the Run still completes honestly, and the model receives the refusal text (so the user-visible answer cannot claim the write happened). A malformed persisted policy (`effect: "permit"`) fails closed with the same observable outcome instead of falling back to allow.
- "an approved tool replay is still blocked when the rule changed to deny": an `ask` rule routes through the existing Intervention/Approval card; the rule flips to deny while the card is pending; after the owner approves, the executor re-reads the policy at the replay boundary and blocks the call — the approval is recorded, but the effect never executes and no file is written.

Permission boundaries confirmed alongside these traces: `allow` only bypasses the Capability decision, never file, Connector, Space or credential authorization; `ask` reuses the existing approval path; AgentScope helpers keep only the read-only subset of the parent's backend tools (`subagent.permissionInheritance: "subset-readonly"`, enforced in Java). There is intentionally no policy editor in this slice; the persisted Bot column is the only rule source.
