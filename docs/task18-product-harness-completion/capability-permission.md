# Task 18.4 capability permission model

`Bot.capabilityRules` is an optional JSON array validated against the version-one rule schema (`capability`, `resource` glob, `scope`, `effect`). The executor re-reads it at every resolved tool call, including a replay of a previously approved request. A malformed policy blocks the tool instead of falling through. `deny` wins over `ask`, which wins over `allow`; scope (`bot > user > space`) and literal pattern length break ties. A deny cannot be weakened by a narrower allow. No matching rule leaves the existing approval and resource authorization path in control.

The built-in rules allow `read_file`, require a human ask for `send_email`, and deny `delete_*` against a resource identified as `production/**`. A path, resource identifier, or connector route supplies the resource; an explicit `environment=production` prefixes it. The system does not infer a production environment from arbitrary connector payloads. Deletion with an unclassified target continues through the existing approval path, so this default is **not** a universal production-data detector. Explicit Bot rules can cover additional tool names and known resource identifiers. No rule can create a connector credential, a Space membership, or a file permission.

The design places all version-one rules on a Bot while giving each rule a `space | user | bot` scope. Consequently, scope currently ranks rules within that Bot's own policy; it does not install a policy across all Bots or users in a Space. A future global policy store would need explicit subject identities and a migration. The existing AgentScope helper catalog and backend background tool bridge still enforce read-only tools, and the same Bot policy is checked when those tools execute. Write work must return to the parent Run for its normal approval and permission path.

The Prisma migration applies to a disposable PostgreSQL database. Contract/core checks, capability-rule unit tests, and the full TypeScript workspace check pass. A Web → Java tool attempt with a configured deny rule has not yet been captured as an acceptance trace. There is intentionally no policy editor in this slice.
