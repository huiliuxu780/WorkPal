# Task 18.5 TurnPolicy v2

New Runs store a version-two execution block inside their existing immutable Run orchestration snapshot. The policy adds only constraints: `budget`, `approval{timeoutSec,onTimeout}`, `retry{maxAuto,retryable}`, and `subagent{permissionInheritance:"subset-readonly"}`. It does not classify the user's intent or select an action for the Agent. Ownership, routing, planning, and delegation retain their earlier meaning. A retry reads the saved block instead of recomputing a policy from the current trigger. An owner-approved budget increase is the explicit mutable `Run.budgetOverride`; it is applied on top of that saved block.

Version-one execution blocks remain readable. They are upgraded in memory using the documented defaults: interactive 200k tokens/$1/900 seconds/50 tools; unattended 500k tokens/$3/3,600 seconds/150 tools; approval expiry after 24 hours; two conservative automatic retries; and read-only helper inheritance. Existing `delegation.maxChildren` and `maxDepth` are upper bounds on the corresponding budget values. A malformed version-two constraint block disables planning and delegation instead of silently restoring broader defaults.

The current AgentScope harness runs a **flat helper fan-out**: helpers cannot nest, so any positive effective `maxDepth` executes at most one real layer; the value acts as a delegation bound rather than a multi-level tree limit. Java computes the tightened effective depth as `min(delegation.maxDepth, budget.maxDepth)` (an explicit zero is preserved, absent or negative values fall back to 1) and treats **zero as an explicit disable of the whole subagent surface**: `delegationAllowed()` returns false, so no native spawn tool (`agent_spawn`, `agent_send`, `agent_list`, `task_*`) is exposed to the model, `backgroundAllowed()` returns false, and the spawn repository is never wired for subagents — neither a synchronous nor a background spawn can execute. Positive depths keep the existing one-layer behavior unchanged.

The TypeScript adapter carries the version and constraints to Java `RunRequest.TurnPolicy`. Java validates v2 fields, preserves v1 parsing, and caps native helper count by both delegation and budget. The backend remains the authority for token/time/tool budgets, wait expiry, retry and tool permission decisions. The dollar limit (`maxCostUsd`) is present in the policy only as an unsupported compatibility field: it is parsed and validated but never enforced, no price source exists or is planned, and it is not a future product goal. Lease-loss retry is now implemented on the Task 18.3 reliability slice: an expired running lease with a persisted active Attempt passes the same no-tool/no-effect gate and 5/30-second schedule as a transport failure, and an unsafe attempt ends as an explicit unconfirmed-outcome failure (`lease-loss-recovery.postgres.test.ts`). AgentScope cannot resume an interrupted model stream, so a retry always starts a fresh Attempt against the persisted Run context and the same stored policy.

TypeScript policy/snapshot/wire tests (`turn-policy.test.ts`, `orchestration.test.ts`) and Java `RunRequestPolicyTest` / `InterruptibleTaskRepositoryTest` cover v1 compatibility, v2 round-trip, helper bounds, a malformed v2 block, and absence of an action selector. On top of those tiers, `packages/adapters/src/turnpolicy-v2-agentscope.integration.test.ts` is a real TypeScript→Java cross-language acceptance: the policy is generated by the production builders (`resolveTurnPolicy` / `buildRunOrchestration` / `turnPolicyFromRun`), travels over the real HTTP wire through a test-side recorder (no production debug endpoint), and is enforced by the real Java runtime. It proves: (1) new Runs carry `version: "v2"` with `budget`, `approval`, `retry` and `subagent` groups and no intent/action/next-step fields (exact wire key-set assertion); (2) Java executes against the tightened effective `maxChildAgents` — a background spawn is refused at the hard count when the stored budget (0) is below `delegation.maxChildren` (3) — and against the tightened effective `maxDepth`: a stored budget depth of 0 hides the entire native subagent surface and refuses both a synchronous and a background spawn attempt ("hides the whole subagent surface and refuses spawns when the tightened depth is zero"), while the default depth 1 keeps delegation available; (3) `subagent.permissionInheritance` is `subset-readonly` and a corrupted wire value is rejected fail-closed with HTTP 422 before any model call; (4) attempts reuse the stored creation-time policy, with the user-approved `budgetOverride` as the only wire budget delta (decreases ignored); (5) a corrupt stored v2 snapshot degrades to planning/delegation disabled and Java hides the native plan and spawn tools entirely. End-to-end, the real Web budget chains in `budget-acceptance.spec.ts` execute on v2 chat/automation policies through the same wire. See [scenario-validation.md](./scenario-validation.md).
