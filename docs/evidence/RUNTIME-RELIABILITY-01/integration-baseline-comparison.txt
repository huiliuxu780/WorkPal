## why it is red (stale expectation, not a defect introduced here)
journeys.test.ts:2063-2064 expects BOTH mentioned bots to produce a Run:
  expect(runsAfterMention.some((run) => run.botId === botA.id)).toBe(true)
  expect(runsAfterMention.some((run) => run.botId === botB.id)).toBe(true)
The shipped product rule in packages/core/src/product-harness/response-owner.ts
(resolveExplicitTurnOwner) is that with several explicit mentions and no
separate-answers marker, only the FIRST mention owns the turn. So botB never
gets a Run and the second assertion cannot hold. Recorded as a stale expectation
since RT-22 (#111); the same rule already invalidated the equivalent assertion in
apps/web/e2e/group-chats.spec.ts.

## note on running these tests
pnpm exec vitest run packages/testkit/src/journeys.test.ts on its own reports
'41 skipped' and exit 0 — the harness sets the env the tests gate on. Only
'pnpm test:integration' actually runs them, so a direct vitest invocation must
never be read as a pass.
