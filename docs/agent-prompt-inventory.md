# Agent prompt inventory

Inventory of **WorkPal's current production prompt inputs**, reconciled against `main @ c2dfea4` on 2026-10-19 by [AG-03](./tasks/AG-03.md). This is the repository-maintained successor of the external baseline (`myagent/docs/workpal-baseline/agent-prompt-inventory.md`); it is not a second prompt implementation. IDs P01–P14 are review handles with pinned markers in the [case registry](../packages/adapters/src/__fixtures__/scenarios/case-registry.ts); AG-04 turns the fixed bodies into independent files with stable segment IDs. The [scenario matrix](./agent-scenario-matrix.md) uses the same handles.

The application backend owns identity, authorization, durable Thread/Message/Task/Run state, files, effects and audit. AgentScope Java is the only production agent executor. PostgreSQL holds the complete conversation; AgentScope's persisted state is working context. A prompt never grants a tool, credential, resource or permission.

## Assembly path

1. The backend selects the Run, its persisted TurnPolicy, model, history, recalled memory and effective backend tools in [`executor.ts`](../packages/adapters/src/executor.ts). The tool list is assembled **per Run**, not recomputed for every model call within that Run (per-call re-trimming is AG-05 scope).
2. The TypeScript adapter sends `prompt`, `instructions`, `history` (with typed provenance), `tools`, `skills`, identity, TurnPolicy and collaboration context to Java in [`agentscope-runtime.ts`](../packages/adapters/src/agentscope-runtime.ts). Auxiliary calls supply their own isolated inputs under dedicated scopes.
3. [`PromptComposer`](../services/agent-runtime/src/main/java/com/workpal/runtime/PromptComposer.java) builds the Java system prompt in order: **platform → content-trust-rules (AG-06, fixed bytes) → turn-policy → bot-instructions → collaboration-context (chat only) → runtime-context (product + execution scope)**. [`platform-instructions.md`](../services/agent-runtime/src/main/resources/platform-instructions.md) is the platform text. The external baseline omitted the trust-rules segment; the order above is the corrected contract (pinned by the integration capture's section-order assertion).
4. AgentScope runs the model and its native tool loop. Backend tools return through the authenticated Tool Bridge, where WorkPal applies its product permissions and approval/effect path.

Injected historical context (compacted summaries, recalled memory, durable memory) rides in **history messages with typed `application` provenance** (`contextKind: compacted_summary | semantic_recall | durable_memory`, generation-fenced; AG-07). Source classification uses these typed fields, never text-prefix recognition. Do not infer prompt priority from a string's source file alone.

## Review and test contract

- An edit to a family must identify affected scenario rows via the registry (`promptFamilies` per case) and preserve the authoritative backend gate. The scenario-contract suites fail when a marker disappears from its composer or a family leaks into a shape that excludes it.
- Family markers are pinned in [`case-registry.ts`](../packages/adapters/src/__fixtures__/scenarios/case-registry.ts) and asserted three ways: unit (composer output), integration (final model request at the real boundary), postgres (production chain). AG-04 replaces markers with stable segment IDs without changing bytes.
- A prompt-only unit test verifies assembly, not model task quality. Real-model quality for these scenarios is **not evaluated** by AG-03/AG-04 (no paid inference); nothing here claims injection resistance against real models — the AG-06 suite pins delivery of the fixed rules only.
- Do not import a new prompt family from external designs merely because it has an ID. Proposed periodic distillation, side-question, room-turn and remote base-prompt replacement flows have no WorkPal production contract.
- Next step per roadmap: [AG-04](./tasks/AG-04.md) moves the fixed bodies of P01–P14 into `prompts/` files with zero byte change to final requests.
