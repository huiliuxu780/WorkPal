## Where progress is recorded

This file is the **single project-level entry point and planning index — but not the source of code truth**. Reading order is exactly three layers, and nothing else:

1. **This roadmap** — where the project is and what comes next.
2. **The item's task card / REQ / spec** (`docs/tasks/*.md`, the `myagent/docs/**` REQs) — how that item is done and what it must satisfy to be accepted.
3. **GitHub PR / `main`** — whether the code actually exists, is reviewed, and is merged.

Do not reconstruct current progress by stitching together `implementation-status.md`, `task-implementation-audit.md`, the assorted `*-progress.md` notes and PR threads — those are evidence archives that this table points into, not competing indexes.

Every row uses exactly one status: `not-started` (no implementation or spec work begun), `in-progress` (implementation, verification, or the item's own spec/decision process actively underway — the row must name the live branch/PR, or for spec-stage rows the in-flight deliverable and its pending decisions), `done` (completion evidence linked **and merged into `main`**), or `blocked` (the reason and needed decision/external change linked). Status discipline:

- `done` → requires merged evidence: the PR link into `main` plus the delivery note/tests. A design review, code audit, or written REQ alone never changes `not-started`; a REQ/spec update alone never makes a row `done`.
- A delivered-but-unmerged PR → `in-progress`, annotated **ready-to-merge**; never pretend `main` already has it.
- `in-progress` → a working branch/PR must exist and be named, except for explicitly spec-stage rows (none currently), which must name the in-flight deliverable and the decisions they wait on, and decision-approved rows awaiting an implementation gate (currently UX-01, see [`docs/ux/UX-01-decision.md`](./ux/UX-01-decision.md)), which must link the approved decision and name the gate they wait on.
- `main` merged **and** the card's acceptance gate passed → only then `done`.

When work starts or completes, update its status here and add the branch/PR link, actual tests, and changed decisions to the relevant implementation note. Keep AV-00 decisions only in [AV-00-decision.md](./avatar/AV-00-decision.md); this table points to that record and reflects whether the gate is closed. Keep technical evidence in targeted tests. Do not create a second status table in the UI or treat external design documents as writable task ledgers. No external message, issue, task or PR is created by this planning record.
