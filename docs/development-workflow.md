# 开发与验收流程

长期约束见 [AGENTS.md](../AGENTS.md)。本文件规定如何选择验证范围和组织交付；命令定义以 [根 package.json](../package.json)、受影响包的 `package.json` 和 [Runtime pom.xml](../services/agent-runtime/pom.xml) 为准。调整流程时在原位置修正冲突规则，历史交付记录保留并注明其适用时期。

## 交付单元和任务书

交付单元是可独立验收、可回退的一组行为变更。默认一个单元对应一个分支和一个 PR，子任务用一个或多个提交推进。单元边界取决于行为和依赖，不按文件数量、任务编号或整条工作流机械划分。

派工前在任务书中写清：

- 所属交付单元、包含的任务 ID、分支、基线和负责人。
- 目标行为、允许修改范围、禁止改动内容和跨单元依赖。
- 实际运行的验收场景、命令、环境、预期结果、证据目录和交付清单。
- 修 bug 时的复现方式、同一回归用例的先红后绿要求。
- 涉及页面时引用已确认的可运行原型、原型说明及具体场景，列出视觉约束和截图验收方式。截图可以补充原型依据，不能替代尚未完成的原型确认。

同一单元内，前置任务的提交通过定向验证后即可继续后续子任务，不等待子任务 PR、完整 CI 或 review。跨单元依赖默认等前置能力合入 `main`；不得复制前置实现绕过依赖，也不默认建立 stacked PR 队列。公共契约成为跨单元依赖时，应先作为范围明确的交付单元验收。

## 开发循环

1. 开工先检查工作区、分支、已有改动和相关基线。保留他人未提交内容；基线失败时记录原因，不能把环境失败计作缺陷复现。
2. 依赖发生变化、需要处理集成问题或交付前，获取最新 `origin/main`，按需 merge；不按日历强制每日 merge，不重写共享分支历史。同步后验证受影响场景。
3. 每次完成一个有意义的行为或契约变更，运行受影响包的类型检查、定向测试及必要的真实链路。提交应完整、可检查，避免为单个类型改名制造临时兼容层。
4. 修 bug 时，先用回归用例证明目标缺陷，再修实现。保持同一用例和有效断言，禁止用 `skip`、`it.fails`、放宽断言或模拟成功掩盖失败。
5. 单元交付时集中运行适用门禁并做 review；不在子任务之间启动 PR、完整 CI 和 pr-watch 循环。当前 CI 仍可能随 push 自动触发，本规则不授权修改触发方式或绕过检查。
6. 检查失败先阅读输出并复现，区分代码回归、环境问题与不稳定测试。回归来源不明且有可靠的好坏基线时再用 `git bisect`。修复以新提交追加；行为改变后重跑受影响验证并核对最终 head 的 CI。

## 验证选择

以下是当前已有入口，不是要求每次全部执行。执行前核对对应脚本、测试文件及环境前提，不把空测试集或未启动的依赖服务算作通过。

| 变更 | 验证入口与要求 |
| --- | --- |
| TypeScript | `pnpm --filter <包名> check` 和 `pnpm exec vitest run <测试文件>`；测试文件可能需要数据库或其他服务，不能只凭扩展名认定为纯单测 |
| Java Runtime | `pnpm test:agentscope`；开发中可用 `mvn -q -f services/agent-runtime/pom.xml test -Dtest=<测试类>` 定向执行 |
| 数据库、迁移 | 运行受影响的真实 PostgreSQL 测试，验证迁移及数据约束；已有集成入口为 `pnpm test:integration`，具体选择按任务场景确定 |
| AgentScope 执行、工具桥接、Worker 调度 | 按影响执行 `pnpm test:e2e --runtime=agentscope --spec=agentscope-product.spec.ts`、`pnpm test:worker-chain` 及对应 Runtime 测试；验证服务、数据库和工具往返事实 |
| 单元交付 | 运行适用的 `pnpm lint`、`pnpm check`、受影响测试和真实链路；逐项对照 [CI 配置](../.github/workflows/ci.yml)，确认相关检查实际执行 |
| 纯文档 | 检查文档内容、相对链接、命令存在性和相关生成物；文档有现成验证器时运行它，不启动无关服务 |

改变鉴权、启动配置、TS 与 Java 协议、工具桥接、session admission 或执行恢复行为时，不能只凭内部函数测试验收。证据必须覆盖受影响的实际启动路径；testkit 的启动配置不能自动证明 `pnpm dev:app` 或部署配置正确。真实 Java Runtime、确定性模型夹具和真实模型调用应分别标明，不能互相冒充。场景依赖真实模型行为时才要求真实模型调用，并记录模型与环境。

发现某条启动路径缺少自动化覆盖时，在对应任务记录缺口、复现和临时验证方式，并补针对该路径的回归；不要永久依赖人工工具调用。

写入门禁前先确认命令真的存在并能运行：`pnpm test:unit`、`pnpm test:postgres`、`pnpm test:process`、`pnpm test:ci-select`、`pnpm test:inventory`、`pnpm test:docs` 已在根 `package.json` 落地（2026-10-28 在 `a409140` 实测：`test:ci-select` 100 项通过，`test:inventory` 覆盖 563 个测试文件、0 错误）。`evidence:check` 仍未实现，不能当作门禁引用；新增命令落地后再更新本节和上表。

## 证据与前端验收

任务书指定唯一证据目录，例如 `docs/<模块>/evidence/<任务ID>/`。交付说明按场景列出执行命令、环境、基线或交付版本、结果及证据相对路径。

- Bug 保留 `red.log` 和 `green.log`，记录同一回归用例、复现基线、修复版本和退出码。红色输出必须因目标缺陷失败，绿色输出必须证明该缺陷已修复。
- 接口保留脱敏请求与响应；执行链保留关联的 Run/Attempt、Runtime 和数据库事实。移除凭据、Cookie、真实用户数据和私有地址，使用可关联的测试标识。
- 页面保留实际操作和截图，并逐项对照已确认原型。默认覆盖 1280 与 390 CSS 像素宽度、浅色与深色；不适用的组合在任务书说明原因。截图不能代替交互操作和状态验证。
- 审核者必须实际打开相关证据，确认场景、版本和结果对应。自动检查只能验证其实现的规则，不能代替语义审核。

## 交付审核与状态

实现者在原分支补齐代码和证据。审核者核对：

1. 最终交付 head SHA 对应的 CI 已完成且通过，相关 job 和步骤实际执行，没有意外 skipped。
2. 本地适用门禁、真实运行证据以及修 bug 的先红后绿证据齐全，证据对应交付行为；已有证据后的修改若影响该场景，必须重新验证。
3. 任务书中的每个场景都有结果和可打开的证据；缺失项退回同一分支补齐，不另拆补验收任务。
4. 交付清单、任务卡和 roadmap 已更新。证据尚不齐或 CI 未通过时仍为开发或待验收状态；验收通过但未合入时为 `ready-to-merge`，合入后才为 `done`。部署状态单独记录。

合并、部署等授权边界以 AGENTS.md 为准。仅完成本地检查不能宣称最终 CI 已通过或建议合并。
