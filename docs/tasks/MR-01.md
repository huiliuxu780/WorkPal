## 产品目标

任务失败或用户停止后，用户能在任务中心或对话中的失败执行卡点击“重试”。系统在原 Task、原 Thread 中创建一次新的 Run，真实入队执行，界面可看到这次重试的进展与结果，也能回看原失败记录。

交付包括产品契约、数据库关联、API、Worker 入队、效果复用、Web 操作、审计和端到端验收。不能只交一个按钮、状态变更或方案文档。

## 已核实的代码事实

- `packages/db/src/retry-runs.ts` 的 `scheduleAutomaticRunRetry` 是自动重试：同 Run 新 Attempt，经 lease/fence 和既有重试政策继续执行。不能把这个函数改名后当手动重试交付。
- Task 有 prompt，Run 有 sourceMessageId、routineId、trigger、orchestration、clientNonce、租约和 Attempt。现有 Run 的 `@@unique([spaceId, clientNonce])` 可作为请求幂等机制的复用点。
- `packages/contracts/src/rpc.ts` / `apps/api/src/router.ts` 的 runs 有 list/detail/executionSnapshot/taskCenter，目前没有手动 retry mutation。
- ExternalEffect 按 Run 关联；工具 key 由 runId、工具、参数和 occurrence 生成。新 Run ID 会产生新 key，因此“创建新 Run”本身不能保证旧操作不重复。
- UI 复用 `TaskCenterView`、`ExecutionCard` / `ExecutionShell` 与现有导航。UX-01 的 Plan-only 进度和 surface 出现规则继续适用。

开始时重新定位这些事实，补齐 Task/Run 创建、jobs 入队、Thread generation、外部镜像消息和 effect replay 的真实调用点，记录到交付说明，不凭过期行号实施。

## 本任务产品规则

### 1. 什么可以重试

- 当前用户可操作、当前 Thread generation 中的 root Run，终态为 `failed` 或 `cancelled`。
- 普通个人对话、群聊 owner 的工作、routine 的单次执行、已接入的外部任务都按同一 Task 重试；保持原 Bot、Thread、任务目标、源消息和入口的隐私/投递约束。
- routine 重试仅重做该次 Task，不新建/修改 schedule，不改变下一次调度时间。
- 自动生成的 delivery Run、辅助模型调用、support/helper 子执行没有独立重试按钮；它们属于所属 root 工作的链路。handoff 后的当前 root owner 按真实所有权判定，不把“另一个 Bot”误当 helper。
- queued/running/waiting/completed 不提供手动重试。等待审批/输入继续使用既有处理入口；完成后的“再做一次”是不同产品操作。
- Thread 已清空、目标 Bot 已删除或用户失去访问权时不能复活旧任务。不是根据浏览器旧状态直接创建 Run。

### 2. 同 Task、新 Run、原记录保留

- `taskId`、`threadId` 不变，新 Run ID、新 Attempt、独立的 Plan/Steps/Todos/用量/结果记录。
- 关联记录直接前驱 `retryOfRunId`；能追踪整个手动重试链。旧 Run 保持 failed/cancelled，旧 Attempt、效果和审计不改写为成功。
- 原始任务目标来自受信的 Task/源消息与既有入口元数据，不能把上一轮错误文案、展示 snippet 或模型生成的重试建议当成新目标。follow_up/skill 等若 Task.prompt 不是完整输入，应按真实持久化结构重建必要输入。
- 仍是原来的长期 Thread，不创建新的用户会话；新 Run 的任务说明明确这是哪一次任务的重试，并携带已完成工作的实际结果，避免模型误认为是新用户消息。
- 重新加载当前模型配置、连接、资源权限和记忆，基于保留的入口/协作身份构造本次不可变 orchestration。旧批准不自动授权新操作。
- 预算使用本次正常创建 Run 的规则；对预算耗尽，界面明确说明需要调整的预算，并复用已有调整入口。不得反复把必然失败的 Run 入队，也不无限继承已耗尽账本。

### 3. 已有工具结果与外部操作

手动重试的含义是完成同一个任务，已确认完成的同一操作复用结果，未完成的部分继续执行。不能把“存在任何 effect”当成整项功能不可用，也不能一律给外部请求换新 key 再发一次。

实施以下明确规则：

| 已记录的操作状态 | 重试行为 |
| --- | --- |
| 已确认完成且结果可恢复 | 同重试链、同稳定 `operationId`、同工具/目标/规范化参数的相同操作返回已有真实结果，不再次调用外部服务；审计链接原 effect |
| 确认未执行或执行前已拒绝/取消 | 按当前权限和审批正常尝试同一 `operationId`，不复用旧批准 |
| executing/uncertain，外部结果未确定 | 按已有 provider 查询/幂等机制核实；可确定时转为前两类。无法确定时把该具体操作交给用户确认处理，暂停该操作，不虚构成功或偷偷重发 |
| 未绑定 `operationId`，或参数/目标变化 | 视为新操作，走正常工具执行与审批；把已有 id 绑到不同参数返回 `bind_mismatch` |

- 复用范围只在服务器记录的这条重试链中，不扩展为整个 Task/Space 的通用结果缓存。同参两次合法操作各有自己的 `operationId`，不能仅以 tool+args 合并。
- 优先延用原 effect 的执行标识及 provider 幂等键/既有回放机制，建立新 Run 到原 effect 的引用；不伪造一条“已完成”的新外部操作。
- 可重复读取仍可读取当前状态；shell/任意连接器调用不能仅凭名称假定只读。复用与未知结果处理以现有操作分类和已记录结果为依据。
- “结果未知”的用户处理必须进入真实 Intervention/可审计决策：能核实已完成则登记实际结果；用户明确确认未发生并授权重新尝试才重新执行；取消则保持不执行。界面说明针对哪个操作，不能用无含义的“仍然重试”绕过。
- 上述是本次重试的业务语义，只为重试接入现有执行链路，不新建全局权限引擎或通用事务框架。

### 4. 点击、并发与执行入队

- 建议 `runs.retry({ runId, clientNonce })`；返回原 Run ID、新 Run ID、Task ID 和导航所需目标。具体 schema 与现有 contract 风格一致。
- 同一点击因网络重发，返回同一个新 Run。重试按钮显示提交中；失败可再次提交并保留该次 nonce，成功后下一次真正重试使用新 nonce。
- 同一旧 Run 的并发手动重试只创建一个后继 Run；另一请求得到已经创建的后继及正确导航。后继结束后再次重试，应从最新失败/取消的后继发起。
- 锁定与创建使用现有 Thread/Task 并发纪律：目标 Thread 已有工作时，按现有规则明确返回冲突或既有队列行为，不建立另一套并发策略。终态重试不能在旧运行仍实际占用租约时重放副作用。
- Run 创建和 jobs 发布遵守项目现有事务/持久化模式。响应丢失或 Worker 暂停不丢任务；恢复后由真实 Worker 领取。
- 新增可识别的手动重试请求事件，记录 actor、来源 Run、新 Run 与 Task；不混用自动 Attempt 的 `run.retried` 事件语义。具体事件名加入 contract 并测试。

### 5. Web 交互

- 失败执行卡：“查看原因”保留，旁边增加“重试”。Task Center 的 failed/cancelled 条目或已有详情提供同一操作。
- cancelled 且不符合 UX-01 surface 条件时，不为了按钮强行制造 Execution shell；用户从 Task Center 重试。
- 服务端返回可重试性与明确原因，两个入口使用同一判断/mutation，不在各页面复制状态规则。Task Center summary-only 可通过现有详情加载补充操作信息，不能为全部条目 eager-load 全量 detail。
- 无已知外部副作用的任务点击后提交；涉及已执行/未知结果时，展示具体状态与上述处理方式，不增加每次都出现的笼统风险确认弹窗。
- 成功后打开/定位原对话中新 Run，显示 queued/running 等真实状态，结果只显示一次；旧失败记录仍可查看，并标明“已重试”与后继入口。
- 网络失败显示可读错误并可重试提交；权限/线程清空/并发冲突显示对应业务原因。按钮 loading/disabled、键盘操作和 aria 文案完整；文案走 Lingui。

## 验收标准

1. failed/cancelled root Run 的正确入口可用，其他状态和内部 delivery/helper 不出现错误操作入口。
2. 新 Run 同 Task、同 Thread、lineage 正确；旧 Run 和 Attempt 历史完整。
3. 原任务输入/附件或技能引用按原持久化数据恢复，真实模型请求能看到原目标与重试上下文，不能只断言“Run 创建成功”。
4. Worker 停止时新 Run queued、无模型请求；启动后领取同一 Run 并完成，自动同 Run Attempt retry 行为不被改坏。
5. 双击、请求重发、两个不同 nonce 并发请求不会创建多个直接后继；失去响应后再次提交能找到相同 Run。
6. 原操作完成后后续模型失败：手动重试完成任务，已完成的同一外部动作计数仍为一次，结果来自真实记录。
7. 同工具参数不同、目标不同和未绑定/不同 `operationId` 不能误命中旧结果；重试链之外不能借用 effect。
8. uncertain 操作有真实核实/用户处理路径，不自动重发；当前权限撤销或原审批拒绝仍按实际政策处理。
9. 群聊 owner 和 routine 单次重试均成功；routine schedule 不变；外部任务保持原频道隐私和已有出站去重约束。
10. Thread Clear、Bot 删除、跨用户/Space 调用、当前执行冲突按上述业务规则返回；无错误 Run 或外部动作。
11. 预算失败有可完成的调整→重试路径；模型/连接配置变更后本次运行使用当前配置。
12. 对话卡与 Task Center 两入口都走通；取消无 shell 的任务也可从 Task Center 重试；结果一次、旧记录可回看。
13. API/事务、effect 复用、Worker、Web 状态分别有测试；关键 end-to-end 场景使用真实 DB 与生产 executor，不用 scripted 假结果证明外部副作用复用。
14. 类型检查、定向测试、迁移演练和新增 E2E 常驻 CI；交付说明给出验收逐项证据。
