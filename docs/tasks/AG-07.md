# AG-07：消息与注入历史的类型化来源

状态：`done`。实施分支 `codex/ag07-message-provenance`，基线为 ME-00 合并提交 `8d263ad`。DEP-01 的生产追平演练与本项实现没有代码前置依赖，不等待 ECS 切换。此任务书由现行代码与 `myagent/docs/WorkPal-agent-upgrade-plan-for-codex.md` 的 19.6 节校核而成；实施证据见 [AG-07 交付说明](../ag07-message-provenance.md)。

## 目标

让 PostgreSQL 中的产品消息具有由可信后端写入的作者与来源类别，并让送往 AgentScope 的 Run history 为真实消息、应用摘要、语义召回和持久记忆携带类型化来源。消费方据此判断来源和生命周期，不再把 `role=user`、正文前缀或伪造的标签当作“真人授权”或“可删除的应用上下文”的证明。现有 Web UI 和消息 API 的外观、顺序及功能保持兼容。

## 已核实的基线与错误前提

- `Message` 目前只有 `role`、`botId`、`runId` 等字段，没有可信的 `authorUserId` 或 `originKind`；多个非真人入口也写 `role=user`。因此不能从 role 推断作者。`createThreadMessageInTransaction` 是中心写入函数，但仓库另有直接 `tx.message.create` 路径，必须先逐一盘点。
- `AgentRunRequest.history` 与 Java `RunRequest.HistoryMessage` 当前只有 `id/role/content/images`。AG-06 的 `refreshApplicationContext` 用文本前缀识别应用摘要、召回和持久记忆；任意正文若撞上这些前缀，来源分类就可能出错。为模型保留可读围栏可以，但代码上的身份判断必须来自可信字段。
- `clearThread` 当前会删除该 Thread 的 `Message`/`Event`，清除应用压缩摘要并推进 generation；本项不得把它重新解释为“保留全部消息、只加清空事件”。完整聊天记录的权威存储仍是 PostgreSQL；AgentScope 状态是独立工作上下文。
- PR #45 留下的原生 `__compaction_summary__` 持久记忆删除 P1 已由 ME-00（PR #47）用持久记忆指纹和可信 history 重建闭合。AG-07 的 provenance 字段不替代这套失效机制；更换应用上下文识别方式时必须保留 ME-00 的更新、清空、跨 Run 重建与非记忆早期对话保留回归。

实施取证更正：上文“另有直接 `tx.message.create` 路径”是待核查假设；生产检索发现唯一的直接 Prisma `message.create` 正在统一写入函数内部，没有第二条独立写库路径。详见交付说明的入口清单。

## 先取证，再定最终契约

1. 列出所有生产 `Message` 写入入口及其调用链：Web 发送/回复、即时通讯入站、webhook/外部连接、Routine/自动化、Bot 间消息、模型回复、delivery、系统合成 wake/ack、审批/介入和其他直接写库路径。给每条路径标出经过认证或验证的 actor、预期 `authorUserId`、来源类别、是否进入模型历史，以及原有 `role/runId/trigger`。不要用测试文件中的写入数量代替生产入口清单。
2. 追踪 PostgreSQL Message → history selection/compaction → TS adapter → Java RunRequest → AgentScope 持久化/恢复的真实传输。特别证明 Java 如何在跨 Run 恢复时保留或重建类型化应用上下文身份；若 AgentScope `Msg` 不能可靠存元数据，选择可信 sidecar/稳定键或独立注入载体，不能悄悄退回匹配正文前缀。
3. 取至少三个现状反例：`role=user` 但来自 Bot/webhook；恶意正文伪装为应用上下文前缀；旧消息来源不明。捕获其当前分类与风险，作为红色基线。区分“来源可证明”和“内容是否可信/是否构成授权”。

## 实施任务

1. **数据库迁移。** 给 `Message` 加可空 `authorUserId` 和非空、可演进的 `originKind`（至少区分 `human_web`、`human_messaging`、`webhook`、`automation`、`bot`、`unknown`；若盘点发现系统合成消息需要独立值，明确增加）。旧行一律保守回填 `unknown`，不根据正文、`role` 或缺失的 `runId` 猜真人。迁移可重复执行；回滚不删除原消息或把历史重新解释为授权。`authorUserId` 仅在可信认证身份存在时填写，不靠客户端提交。
2. **收紧写入边界。** 在可信服务端入口派生作者和来源，再通过统一写入接口传递到 DB；模型、工具、网页内容和客户端 payload 不能设置或覆盖这两个字段。直接 `message.create` 路径要么迁入共同接口，要么有显式来源和定向测试。新增路径缺省成 `unknown` 时不得被后续权限/记忆逻辑当真人；对入口遗漏增加扫描/测试或约束。
3. **类型化 Run history。** 在 TS 契约、序列化与 Java `HistoryMessage` 中加入稳定、可验证的来源描述：真实消息引用其 DB 来源；应用压缩摘要、语义召回、持久记忆分别有明确的 synthetic/application-context kind 与必要的 generation/revision；老协议或旧持久化数据以 `unknown` 处理。字段只由可信后端组装，禁止模型正文塑造 provenance。为既有消费者保留兼容迁移路径，并在交付说明中固定最终 wire schema。
4. **替换文本识别。** Java 的应用上下文刷新/清除、合成 wake/ack/delivery 的识别，以及 TS history compaction 的合成消息筛选，逐步改为类型字段与可信 `role + trigger + runId` 等组合。正文前缀可以继续提供给模型阅读，但不再决定身份或授权。空但非 null 的 history 继续表达“清除旧应用上下文”；null 继续表达“调用方未提供历史信息”。
5. **兼容与范围。** 现有 API/UI 消息排序、分页、引用、未读、群聊和消息展示不因新增字段而改变。Thread Clear 继续实际删除旧消息并使旧 generation 的摘要/注入历史不可达。不要顺手建立 ME-01 的事实存储，也不要启用原生 helper、Pi 或新的模型权限。

## 验收标准

1. 生产消息入口清单完整且逐项有测试：真人 Web/消息通道、webhook、Routine、Bot 协作、模型回复、delivery 和系统合成路径写入与其可信来源一致；模型或外部 payload 伪造 `authorUserId/originKind` 被忽略或拒绝。`role=user` 本身不能通过“真人授权”判断。
2. 旧库迁移后，原消息数量、顺序、内容和 UI 展示不变；旧行是 `unknown` 且不进入只接受已验证真人来源的记忆蒸馏/授权路径。迁移重跑结果稳定；新数据的来源由入口明确填写。
3. TS→Java 的真实 Run 请求在 history 中为普通消息与应用摘要/召回/持久记忆携带类型化来源；Java→模型的最终请求仍按模型协议发送 role/content，不虚称模型能看到后端 provenance 字段。伪造相同前缀、XML 标签或审批声明的普通消息不能被 Java 当成应用上下文，也不能改变权限、role 或工具面。跨 Run 的当前应用上下文更新、清空以及 `history=null` 各按原定语义工作。
4. 应用层压缩输入按类型排除应排除的合成消息，保留真实用户消息；Thread Clear 后旧 generation 的消息和摘要不再进入后续 Run。ME-00 的原生摘要失效与可信 history 重建测试必须继续通过，包括记忆更新、删除、跨 Run 续跑和早期普通对话保留。
5. JDK 21 Maven package、受影响 TS 包类型检查、数据库迁移/回填测试、真实 TS adapter → Java jar → fixture 集成、主要消息入口和历史压缩回归、Web API/UI 定向检查通过。交付说明列出 schema 决策、旧数据处理、前后 wire diff、每个入口的证据及 ME-00 回归结果；路线图状态及 branch/PR/测试结果回填。提交前核对 `git status`/diff，排除密钥、真实用户数据、私有 URL 与本机身份信息。

## 不得扩大的结论

来源字段证明**后端记录的进入路径**，不证明 webhook 内容真实、模型输出可信，也不自动授予工具权限。确定性 fixture 能验证传输和拒绝边界，不能证明真实模型一定不服从注入文本。AG-07 完成不等于 ME-01 的事实纠错/删除，也不能代替 ME-00 的原生摘要失效回归。
