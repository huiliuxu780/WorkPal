# ME-00：关闭原生压缩摘要中的已更新/已删除持久记忆

状态：`not-started`。实施基线：WK-01 合并后的 `main`（`0df02fb`）。本项是 PR #45 评审确认的 P1 的独立修复切片，建议在下一次 Java 生产部署及 AG-07 之前完成。完成时把它作为新增工作项写入 `docs/next-work-roadmap.md`，并链接测试、交付说明和 PR；不要把现有 ME-01 的完整事实记忆设计悄悄改名为本项。

## 目标与已知事实

AG-06 将持久记忆从 system 指令移到了可替换的 user 数据消息。`RuntimeEngine.refreshApplicationContext()` 能在后续 Run 更新或删除这条直接注入的消息；但 AgentScope 原生压缩可能先把它写进持久化 `__compaction_summary__`。该摘要不是应用上下文消息，现有刷新逻辑不会移除，所以之后即使记忆已更新/删除，旧内容仍可能进入模型请求。

根据本次人工远端核查，现运行的 ECS 实例是 2026-10-07 的旧 Python 版本，消息记录此后未增长；上述 Java 路径尚未部署。这个环境判断以提供的远端证据为依据，不能由消息数单独断言完全没有访问流量，也不应假设该 Java 缺口已在生产暴露。风险边界是**下一次生产追平部署**：修复与验证应先于该部署。

## 先取证

1. 在未修代码上用真实 TS adapter → Java jar → 本地 OpenAI 兼容 fixture，建立同一身份、Bot、Thread、session 的多 Run 场景。提供含唯一标记的真实持久记忆；以足够 token 的历史确保原生压缩**实际发生**，捕获 SUMMARY 模型调用、持久化 `__compaction_summary__` 和下一轮正常模型请求。不要把 `triggerMessages(30)` 当作单纯 30 条门槛：AG-02 已证明当前配置还走动态 token cutoff。
2. 分别进行“旧记忆→新记忆”和“旧记忆→无记忆”的后续 Run，先留存失败断言：旧标记仍从原生摘要到达模型。对照一条未触发压缩的 session，证实现有直接应用上下文刷新仍有效。只检查 `refreshApplicationContext()` 返回或直接修改测试状态文件，不算真实边界取证。
3. 记录原生摘要在 AgentScope `AgentState` 中的真实结构、产生时机和跨进程重启行为；列出待审批/工具调用恢复、正在执行的 Run、Thread Clear generation、应用层 `history.compact` 游标与 user/bot scope 的交互，选定修法后再实现。

## 修复约束

1. 在**可信的当前记忆状态**变化后，使下一次使用该 session 的正常模型调用看不到由旧持久记忆注入而来的原生摘要内容。可选方案包括安全失效/重建受影响的原生工作状态，或阻止可替换应用上下文进入原生压缩并保持它按 Run 注入。必须先证明所用 AgentScope 2.0.3 API/状态操作可行；不能用正文字符串搜索、替换标记或让模型“忘掉”来声称删除。
2. 若采用会话失效：从 PostgreSQL 当前 Thread 历史及其应用层摘要重建足够的工作上下文，不把旧记忆重新播种；明确对普通历史连续性、token/调用成本、应用层压缩游标、正在执行/待审批 Run 的影响。持久记忆可能是 user scope（影响多个 Bot/Thread）或 bot scope（只影响该 Bot）：使用每次 Run 可核对且跨 Java 重启持久的版本/指纹或等价机制，避免仅失效正在编辑的一个 session。不要复用 Thread Clear generation 来表示记忆更新。
3. 保持 AG-02 的 `flushBeforeCompact(false)`、`offloadBeforeCompact(false)`、工具结果不卸载和原生 helper 委派停用；不得以全局关闭原生压缩造成上下文无界增长。`history == null` 的辅助/恢复语义不变，空但非 null 的历史仍表示当前应用上下文集合为空。除为修复确需的最小 wire/状态字段外，不提前实施 AG-07 的来源迁移或 ME-01 的事实存储。
4. 只对可证明属于“被替换的持久记忆注入”的旧内容作保证。若相同事实后来被真人在 Thread 消息中重述，或被模型写进独立的正式消息，不能声称删除记忆会抹去这些独立记录；产品上若需要更强的删除语义，应在交付说明中单列。对删除时已在执行中的模型调用，明确生效边界及是否需要取消，不要把“下一 Run 无旧摘要”说成“任何并发调用即时撤回”。

## 验收标准

1. 红→绿真实链路覆盖“更新”和“删除”：压缩确实触发，旧标记进入修复前的原生摘要；修复后下一次模型请求无旧标记，更新路径只有当前记忆，删除路径无持久记忆正文。测试不能仅因未触发压缩或 fixture 不回显标记而通过；破坏性验证撤去失效机制应使回归测试变红。
2. 跨 Java 进程重启仍成立；重复同一记忆版本的 Run 不反复重置状态。user scope 变更影响相关 Bot/Thread，bot scope 变更不误伤其他 Bot；不同 user/Space 不串读。Thread Clear 后旧摘要不可达，应用层 `history.compact` 的 PostgreSQL 游标未被本项暗改。
3. 正常历史工作上下文在修复后仍可用：至少验证压缩后的近期消息与应用层摘要按既有语义进入后续 Run；若某些早期上下文必须丢弃，报告准确的边界和用户影响。待审批/工具恢复、已完成 Run、后台投递及取消路径不因状态清理被静默改写；必要时有定向回归。
4. 无新的原生记忆文件、offload 指针、额外工具暴露或 helper 再启用；正常模型调用与 SUMMARY/FLUSH 的种类和次数按实际修改清楚报告。固定 fixture 只证明请求与状态行为，不证明模型会主动忘记之前学到的事实。
5. JDK 21 `mvn package`、受影响 TS 类型检查与定向集成、现有 AG-02/AG-06 压缩和记忆回归通过；交付文档写明基线、方案取舍、性能/上下文代价、并发与旧数据处理。提交前检查 Git diff 不含凭据、真实用户数据、私有 URL 或本机身份信息。
