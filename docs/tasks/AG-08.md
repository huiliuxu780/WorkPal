# AG-08：撤权后待处理工具调用的可恢复执行

状态：`in-progress`（实现与本地定向门禁完成，待与 AG-05 统一 PR）。分支 `codex/ag05-tool-visibility-recovery`，独立 worktree `WorkPal-ag05`。交付说明：[ag08-permission-revoked-recovery.md](../ag08-permission-revoked-recovery.md)。此项修复 AG-03 发现 A/B，不是新 Agent 执行器。

## 已确认缺口

`S09-C3 permission change before resume`：用户批准连接器操作后撤销权限，Java 的 bridge allowlist 拒绝恢复中的工具调用，provider 零请求；Run failed，effect 仍 approved。会话里 pending tool call 未被消费，长期 Thread 下一 Run 又在模型调用前失败。

当前拒绝守住了授权；需要修复的是用户结果、effect 生命周期与工作会话的继续能力。

## 目标与产品结果

对已撤权操作，用户能看到准确的权限变化原因；模型收到与原 tool_call_id 对应的真实拒绝结果，并能说明任务未执行的部分。之后同 Thread 正常继续；恢复权限后可按当前授权正常尝试。不能自动执行已被撤权的旧操作，也不能假称执行完成。

## 冻结的状态与用户结果

针对本卡的“用户批准→撤权→尚未发送 provider 的 pending 调用恢复”场景：

| 记录 | 必须结果 |
| --- | --- |
| 原外部 effect | `denied`，拒绝来源为当前权限/策略，原因码 `permission_revoked`，明确 `executed=false`；不能停在 approved，也不能写 completed/uncertain |
| 原审批决定 | 保留既有 approved 决定及操作者/审计；策略拒绝不是用户反悔，不能伪造一条用户 deny |
| 当前 Run | 交付真实拒绝反馈和用户可见说明后终态 `failed`，原因 `permission_revoked`，原 Task 保留；不能因为成功输出解释就标 completed |
| 下一普通 Run | 同 Thread、同 generation 正常进入模型并能 completed；不重放旧 pending call |
| 重新授权后的用户新尝试 | 新 Run 按当前权限及审批执行；旧拒绝 effect/审批历史保持原样，不把旧批准当作本次批准 |

模型的拒绝反馈用于说明未执行内容与后续可操作步骤。该失败 Run 不自动替换成另一条有副作用的执行路径。确已发送而结果未知的对照沿用既有 uncertain/人工确认契约，不能套用上表的“未发送”结论。若现有审计事件无法表达“原批准＋执行前策略拒绝”，应扩展类型化事件/原因字段；不能复用 `approval.resolved=denied` 冒充用户决定。

## 实施

- 在恢复 pending call 的唯一权威边界生成类型正确的拒绝结果，并消费这次待处理调用；保持模型协议中的 tool-call/result 配对。严格按上表落 Run/effect 状态和审计事件，避免 approved 悬挂。
- 与 AG-05 每次请求的当前工具面接合，后续模型请求不带撤权工具。
- 同 Thread 下一 Run 保留正常对话、应用上下文与原生压缩状态；不能靠删全部工作上下文、清聊天记录或更换 generation 修复。
- 审批允许/拒绝、未知外部结果、失败重试和进程恢复各自保留真实语义。仅本地权限拒绝可以定性为未发送；真正已发送但结果未知仍走现有 unknown 流程。
- 先把 AG-03 的 A/B 复现转换为目标行为的红色测试，再修实现；更新场景矩阵“已知缺口”为实际新契约，禁止只删除旧失败断言。
