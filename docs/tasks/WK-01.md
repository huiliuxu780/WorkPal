# WK-01：独立 Worker 进程的 AgentScope 拓扑验收

状态：`not-started`。从已合并 AG-01、AG-02、AG-06 的 `main` 开始；完成证据和状态写回 `docs/next-work-roadmap.md`，详细结果写入独立交付说明。

## 目标

用本地 PostgreSQL、本地 OpenAI 兼容模型 fixture 和真实 Java AgentScope runtime，运行彼此独立的 Web/API、Graphile Worker、Java runtime 进程。证明 API 创建的 Run 由 Worker 领取和执行；Worker 中断后能从持久化状态恢复；真实生产 outbox 能在没有新用户消息的情况下主动投递，且用户只看到一条结果。不得把进程内 job handler、`scripted` runtime 或测试直接调用 `delivery.dispatch` 当成这项验收。

## 已核实的前提

- `packages/testkit/src/cli/topology.ts` 和 `infra/compose/docker-compose.topology.yml` 已有独立 API/Web/Worker/PostgreSQL 拓扑，也覆盖“Worker 停止时 Run 排队，重启后完成”，但它固定使用 `AGENT_RUNTIME=scripted`，没有 Java runtime，也没有主动结果投递。应扩展或复用现有拓扑，不重建一套同义 harness；原有 scripted smoke 保持可用。
- 通常的 AgentScope E2E harness 会另起 Java jar，但 job handlers 与 API 在同一测试进程，不能证明 Worker 部署边界。
- 生产 `apps/worker/src/index.ts` 有 Graphile Worker 和 `delivery.dispatch` 定时路径；`packages/adapters/src/result-delivery.ts` 以持久化 `DeliveryRecord` 创建 `trigger=delivery` 的 Run，并在完成后标记 `delivery.sent`。
- AG-02 后，新 Run 的原生 helper 委派在生产入口硬停用。WK-01 不得为了制造后台结果而重新启用它。已有 `apps/web/e2e/budget-acceptance.spec.ts` 的 Routine 超预算场景会经生产逻辑产生 `run_result` outbox，可作为生产可达的主动投递用例；它现有的进程内结果不算 WK-01 完成。
- `infra/compose/docker-compose.prod.agentscope.yml` 仍指向旧 Python runtime；当前主部署的 Java Dockerfile 是 `services/agent-runtime/Dockerfile`。不要把旧 overlay 当作正确的生产拓扑依据。若发现它被文档或部署脚本实际引用，应单独报告影响并做最小修正。

## 实施任务

1. **先留下基线。** 核对现有 topology smoke 与 AgentScope E2E 的实际 PID/容器、runtime 模式、job host、PostgreSQL 和 fixture 连接。记录哪一项验收目前缺失，避免把“脚本拓扑已有”误写成“独立进程完全没有”。检查真实部署 Compose 的 Java/runtime 和 tool bridge 配置。
2. **增加 AgentScope 拓扑。** 在现有 topology harness 上加独立的 AgentScope 模式或等价的可维护入口：API、Web、Worker、Java runtime、本地模型 fixture、PostgreSQL 分别运行；API/Worker 都走生产 AgentScope adapter，Worker 走实际 Graphile 队列；Java 接入可从容器/进程访问的本地 fixture。固定临时数据库、端口、凭据和数据目录，测试结束清理；不依赖付费模型、真实密钥或外网。保留 scripted smoke 的原有含义。
3. **Run 领取与恢复。** 停止 Worker，使用产品 API 创建 Run，断言 PostgreSQL 中它仍为 queued、Java fixture 未收到模型请求。启动 Worker，断言该 Run 的 Attempt/租约及模型请求真实发生，Run 完成且消息由该 Run 产生。再覆盖一次 Worker 在领取后中断或重启的可恢复阶段，按现有租约/重试策略完成或如实失败并可重试；用数据库记录、Worker 日志与 fixture 请求关联同一个 Run，不能仅凭页面出现文字推断恢复。设置有界超时，记录实际恢复耗时。
4. **主动结果投递。** 采用生产可达的 Routine 超预算路径：通过产品入口创建并触发 Routine Run，使用可控 fixture/时钟或测试 seam 造成真实 budget failure，让生产事务写出 `delivery.created` 与 `run_result` DeliveryRecord。停止/重启独立 Worker，确认它自行执行 `delivery.dispatch`、创建 `trigger=delivery` 的 Run、调用 Java fixture、提交一条 bot 消息并标记 `delivery.sent`；期间不发送新的用户消息，不直接调用 dispatcher，也不手造已完成结果。若现有时钟 seam 无法跨进程复用，可以增加仅测试可达的受控触发，但必须保留生产 enqueue/claim/dispatch/settle 链路并说明 seam 边界。
5. **幂等与隔离。** 重复调度或重启 Worker 后，原源 Run 只对应一个 delivery Run、一条 `delivery.sent`、一条用户可见 bot 消息；用户消息数不增加。再断言其他 Thread/Space 不会看见该结果。若 Java 请求失败或 Worker 中断发生在提交前，不能标记成功；报告实际重试/失败状态。
6. **常驻入口与交付。** 给出一个可重复运行的拓扑验收命令；按仓库 CI 的 Docker 能力决定接入常驻 job 或单独的必跑验证，并说明资源及时间成本。将基线、进程证据、数据库/事件断言、恢复耗时、fixture 调用次数、测试结果和限制写入 `docs/wk01-worker-topology-acceptance.md`。更新路线图 WK-01 状态；提交前检查 `git status`/diff，不纳入本机凭据、私有 URL 或真实用户数据。

## 验收标准

1. API/Web、Worker、Java runtime、PostgreSQL 和模型 fixture 各有可识别的独立进程/容器；API 不执行 Worker job，Worker 不使用 `scripted`，Java 真实收到本地 fixture 请求。拓扑健康检查明确确认 `agentscope`，不能沿用 scripted 的断言。
2. Worker 停止时 API 创建的 Run 保持 queued，且模型调用数为零；Worker 启动后能领取并处理**同一 Run ID**。中断/重启用例用 Attempt、租约、事件和模型请求证明恢复语义，不依赖模糊的最终页面文字。
3. Routine 超预算由真实后端路径产生 outbox，独立 Worker 自动投递；`delivery.created` → delivery Run → bot 消息 → `delivery.sent` 的 ID 和顺序可追溯。没有新用户消息、没有人工 dispatcher 调用、没有伪造后台完成结果。
4. 重复调度及 Worker 再次重启后，该 Thread 的 delivery Run、`delivery.sent` 和对应可见 bot 消息均恰好一个；跨 Thread/Space 不串读。异常发生在完成前时状态诚实，不提前报送成功。
5. JDK 21 Maven package、受影响 TS 包类型检查和定向测试通过；新增拓扑命令在干净临时环境实际通过，并留下可复现的运行方式与资源需求。所有超时有界，测试会清理容器、数据库和临时文件。

## 范围与风险

本项证明**生产可达的 Routine 结果主动投递**及独立 Worker 边界，不声称新原生 helper 的后台结果已在生产拓扑验证。AG-02 的 helper 停用保持不变；其恢复另需安全配置和独立验收。Routine 的预算 fixture 若负载敏感，先用有界同步点和可诊断日志消除 flake，再把它纳入长期门禁。不要为了让测试变绿引入 Pi/Python runtime、关闭授权检查或把 Worker job 放回 API 进程。
