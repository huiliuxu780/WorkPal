# DEP-01：生产从旧 Python 栈追平到 Java AgentScope 主干

状态：`not-started`；这是独立部署任务，**不是** ME-00 的一部分。实施基线须为 ME-00 的长期上下文回归闭合且已合并的固定 `main` 提交。当前任务仅准备可审查的部署方案和演练；实际 ECS 切换在备份、演练、回滚方案和目标提交全部确定后再批准。

## 已知事实与待核实项

- 根据 2026-10-16 的人工远端核查，ECS 现运行的是 2026-10-07 建立的旧 Python `agentscope` 容器，消息表只有 7 条旧消息；Java runtime 与 AG-01/02/06、WK-01、ME-00 尚未在该实例运行。容器创建时间证明没有成功重建，但不能排除所有失败的部署尝试；无新消息也不能证明完全没有读取或登录流量。
- 核查时生产迁移记录据报落后主干 19 项。开工时必须重新读取目标 DB 的 `_prisma_migrations` 与目标提交的迁移目录，固定**实际**待应用集合及顺序，不能沿用口头数字。
- `infra/compose/deploy-workpal.sh` 会快照/回滚远端**源码树**，然后 `compose up --build`；API 启动时执行 `prisma migrate deploy`。脚本不会回滚 PostgreSQL 或持久卷。旧 Python 应用未必兼容新 schema，故“脚本自动回滚成功”不能仅由健康检查证明数据与业务已恢复。
- `infra/compose/backup-prod.sh` 默认 `RAKAZO_DEPLOY_DIR=/srv/rakazo`，而部署脚本默认 `APP_DIR=/srv/workpal`；演练时要明确同一目标目录和 Compose project。该备份脚本覆盖 DB 与 appdata，须另外盘点旧 Python/新 Java runtime state、文件、密钥及其他持久卷的保留/丢弃决定。不得因为仅有 7 条消息就跳过备份。
- PR #46 已删去过时 Python overlay；仍须用部署实际使用的三层 Compose 文件验证最终 `agentscope` 构建自 `services/agent-runtime/Dockerfile`，api/worker 走 `AGENT_RUNTIME=agentscope` 和正确的 tool bridge。

## 准备与演练

1. **只读盘点。** 记录 ECS 当前容器镜像 digest/创建时间、Compose 配置与 project、持久卷挂载、数据库版本和迁移表、磁盘余量、网络/镜像镜像源、生产环境变量名称与必需资源；证据中隐藏地址、用户、密钥和私有 URL。明确哪些数据可以弃、哪些必须恢复，不能由“测试环境”自行推断。
2. **可恢复备份。** 在与目标相同的 Compose project 上备份 DB、appdata 和所有相关运行时状态，校验归档完整性与校验和；在隔离环境实际恢复一次并核对关键计数/对象。确认备份文件不会被后续部署脚本或清理策略覆盖，保留旧镜像与旧源码快照直到验收结束。
3. **迁移副本演练。** 从生产 DB 的已验证副本启动隔离栈，使用目标提交的镜像与迁移目录执行完整待应用序列；核对 Prisma 迁移状态、数据约束、关键实体和现有 7 条消息的可读性。记录耗时、锁、失败点与需要的停机窗口。若迁移不可逆或旧代码不兼容新 schema，写出**DB+文件一致性恢复步骤**，不能只依赖 `deploy-workpal.sh` 的源码回滚。
4. **首次脚本演练。** 在同结构的隔离主机/目录验证 `deploy-workpal.sh` 的磁盘守卫、rsync 排除、三层 Compose 合并、Java 构建、API/Worker/Java/Web 健康、`.last-deployed-revision` 写入。故意制造一次构建/健康失败，验证从失败点开始的回滚；尤其检查脚本在 rsync 或 `compose config` 失败时的半更新远端树，以及迁移已执行后如何恢复 DB。需要修脚本时用单独可评审的代码提交并重跑演练。
5. **上线方案。** 写明目标 `main` SHA、所需维护窗口、负责人、执行顺序、成功判据、观察窗口及止损阈值。成功判据至少包括实际镜像/源码 SHA、Java runtime 健康、API/Worker 分进程工作、迁移全数成功、登录/建 Bot/单次本地 fixture 或受控真实 Run、消息持久化与授权拒绝、无重复投递。保留审计与回滚证据，不把单一 `/health` 200 当作完成。
