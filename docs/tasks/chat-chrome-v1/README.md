## 1. 目标与用户路径

只打通私聊中的这一条路径：

1. 用户发送需求，消息气泡在右侧，使用主题 accent 实色底、白色前景。
2. Bot 在左侧回复文本，并在气泡外展示一张独立的页面交付物卡。聊天内容列最大宽度 704 CSS px，卡片满列。
3. 用户要求更新同一交付物。新版成功发布后，旧位置保留卡壳并显示“已在下方更新”，新消息位置出现最新卡。
4. 点击任意旧卡或最新卡，打开近满屏详情，读取同一交付物的最新已发布内容，不显示版本侧栏或版本下拉。
5. 关闭详情，恢复聊天中的可见位置与键盘焦点。

本任务不重做各卡种视觉，不扩展旁路功能。截图不是执行成功的证明，实际页面必须使用真实消息、交付物内容和持久化状态。

- 当前相关组件使用 `lucide-react`，不是 Phosphor。原需求指定 Phosphor，本文保留这一目标：原型对齐时给出本任务涉及图标的对应关系，仅在本次改动的聊天 chrome 内落实；不执行全仓图标迁移，也不再声称“无需更换现有图标”。

本期页面类型收敛为 Bot 发布的 HTML 交付物，优先映射现有 `file` 消息块及 `text/html` 内容。用户上传附件、PDF、Markdown 和其他卡种不纳入视觉改造。若已确认原型中的“页面”实际对应其他业务类型，必须先修正本条与映射，不能把不同产品对象硬套为 HTML 文件。

本期复用现有后端交付物族与同名更新规则，验收固定更新同一页面文件，不引入重命名、同名独立交付物管理或新的版本系统。前端只消费后端给出的族关系，不自行按标题或文件名归并。交付说明必须注明现有名称规则的限制；若该限制导致主路径无法成立，先报告事实和必要范围调整，不用前端猜测掩盖。

## 3. 行为契约

### 3.1 消息、卡片与布局

- 内容列使用 `max-width: 704px`，在聊天可用区域内居中。空间充足时页面卡外框宽 704 CSS px；空间不足时随内容列收缩。卡宽为内容列的 100%，不能让窄屏产生横向溢出。
- 用户文本右对齐，Bot 文本左对齐。卡片是消息内容区内的独立块，不进入文本气泡或 Markdown 正文容器；保持消息块的原始顺序。
- 同一 Bot 连续文本气泡按单条、首、中、尾呈现接合圆角。用户消息、独立卡片、其他发送者和日期分隔中断分组。布局与间距以已确认原型为准。
- 卡片副标仅显示类型“页面”，不附带版本号或文件大小。卡面不额外显示 v1/v2、版本徽标或历史选择器；不修改用户正文及交付物正文中的合法版本文字。
- 页面卡 v1 只显示真实标题和类型。原型中的示例摘要与“本页目录”不属于本期验收，不从 HTML 正文推测或生成卡面字段；后续需要时先定义真实字段及来源。
- 最新卡整卡 hover 呈现原型规定的阴影抬起；旧卡保留可点击入口与键盘焦点样式。触屏不能依赖 hover 才能打开详情。
- 旧卡保留可识别标题和独立卡壳，展示固定文案“已在下方更新”，具体内容排布以原型为准，不擅自改成语义不同的文案。
- 颜色、边框和阴影走现有主题 token；继续使用 `@rakazo/ui-tokens`、`@rakazo/ui-web`、`@rakazo/chat-ui` 和 `apps/web/src/components/ai/` 的视觉语言。浅色参考色不能直接用作所有主题的硬编码值。

### 3.2 交付物身份与更新

实现必须区分三个概念，字段名可复用现有契约，不要求按下列名称另建实体：

| 概念 | 含义与不变量 |
| --- | --- |
| 交付物稳定身份 | 后端确认的同一交付物族；新旧卡共享，用于解析最新内容 |
| 内容版本身份 | 一次已成功发布的具体内容；保留内部版本数据，不展示版本 UI |
| 卡片展示身份 | 消息流中一次发布对应的展示位置；刷新、重放和重复事件不得新增同一次展示 |

状态以已成功发布、可读取且已关联消息的交付物事实为准：

| 事件 | 原卡行为 | 新位置行为 |
| --- | --- | --- |
| 第一次发布成功 | 无旧卡 | 展示第一张有效卡 |
| 请求更新，仍在生成 | 保持有效 | 沿用现有执行状态，不生成假成功卡 |
| 更新失败或取消 | 保持最后一次成功卡有效 | 不出现成功交付物卡，不提前标旧 |
| 下一次发布成功 | 此前全部展示变为更新态 | 在对应新消息位置展示有效卡 |
| 重放、重连、重复事件 | 状态不倒退 | 同一次发布不重复出卡 |

补充约束：

- 服务端成功发布与消息投影应有一致性保障，不能长期留下“旧卡已失效但新卡没有消息位置”的状态。
- 不以客户端到达顺序、当前已加载消息集合或请求发起时间判断最新版本。
- 刷新、切换聊天后返回、历史分页只加载到旧卡时，仍能恢复正确更新态并打开最新内容。
- 旧消息缺少新增字段时，在统一适配边界使用可验证的后端关联补齐；无法建立关系就暴露明确错误或不可用状态，不静默伪造稳定 ID。
- 只补齐本链路所需的契约、投影和读取能力；复用现有并发与幂等保障。若必须迁移数据库，说明必要性、迁移方式和回退影响，不另建一套版本存储。

### 3.3 详情读取与关闭

- 点击新旧卡均通过交付物稳定身份，在现有用户与资源权限范围内读取最新成功发布的内容。解析最新版本和实际读取处均不能扩大资源可见范围。
- “最新”以本次打开详情时服务端解析到的最新已发布版本为准。详情打开期间不要求实时切换；关闭后重开必须重新解析，不能一直使用首次缓存。
- 标题、内容类型和正文来自同一次解析结果，不混用旧卡元数据与新正文。
- 打开后有明确加载态。加载失败、资源不可用或无权限时显示对应失败状态，允许关闭；可重试的错误使用用户主动重试，不无限自动重试，不回退旧内容冒充最新。
- 详情复用现有 Dialog 或 Sheet。桌面四边留白、最大尺寸、窄屏尺寸和内部滚动区域写入原型说明；“近满屏”不能由开发自由估计。
- 不显示版本侧栏、版本下拉和历史切换入口。不删除后端历史记录，不改变其他页面的版本管理语义。
- 保留现有 HTML 沙箱隔离及访问限制，不能为了预览而放宽脚本、网络、父页面访问或顶层导航权限。
- 关闭按钮与 Esc 可用，焦点在详情内正确管理，关闭后回到触发卡。聊天恢复同一可见消息及其相对视口位置，不跳顶部或底部；详情期间有新消息时也不强制跟随。原触发元素已卸载时，使用聊天容器内合理的焦点位置。
- 若复用的详情中保留下载操作，其文件与当前展示内容一致，不从旧卡下载另一版本。其他页面的下载语义保持原样。
