## 1. 用户结果

用户只面对一份计划：Bot 制订计划 → 用户看具体版本并批准/提出修改/拒绝 → 批准后按此计划执行 → 重要修订重新审阅 → 完成或明确终止。

原生 `plan_enter/plan_write/plan_exit` 和产品结构化 Plan 必须操作同一个计划身份、内容版本与审批状态；不能通过隐藏一套 UI、关闭原生计划，或只复制 Markdown 到展示卡来宣称统一。

## 2. 当前事实与依据

- [UX-01 决策](../ux/UX-01-decision.md) 和 [B](../ux/UX-01B-implementation.md)/[C](../ux/UX-01C-implementation.md) 已实施三层展示、唯一 Plan 进度、外置 Intervention 和历史兜底，本批保留这些规则。
- 现有 `RunPlan/RunPlanRevision` 是 PostgreSQL 结构化计划；Steps/Todos 有独立语义。Java 另外注册 native Plan Mode 和 `workpal-plan-approval`，这正是待统一的两条链。
- 当前 TurnPolicy planning 值为 `disabled | auto`，没有已实现的“manual”档。不凭任务名称新增另一套路由/复杂度模型。
- [AG-05/08](./AG-05.md) 已支持每次模型请求的工具面和撤权恢复；[MR-01](./MR-01.md) 已有稳定 operation identity。计划审批不能扩大执行权限或破坏重试幂等。

本卡把此前留待 UX-02 的审阅范围、修订、拒绝与 Todo 定位写成一致的开发规则。旧 UX-01 的“本期不改 DB/API/Java”限制只属于 UX-01，不适用于本批。

## 3. 本批产品规则

### U1. 唯一计划与是否审阅

- 每个 Run 只有一个当前计划身份；PostgreSQL `RunPlan` 和版本记录是权威。原生工作文件/状态只是同一计划的可恢复投影，不能独立获批后绕过产品数据。
- planning=auto 时仍由模型按任务需要选择是否制订计划，普通短请求不强制规划、不新加复杂度 Router。
- 在可交互且 planning 允许的 Run 中，模型选择制订可执行计划后，提交计划/`plan_exit` 统一进入版本审阅；结构化发布不能作为跳过审阅的第二条入口。草拟前可正常读取资料；提交待审后暂停执行，保留同一 Task/Run。
- planning=disabled 的既有场景不因本批突然要求人工计划审批；工具面、后台/routine/协作场景继续遵循既有 TurnPolicy。确需人工动作的路径使用既有可交互契约，不制造无人能处理的等待。
- 计划审批只同意该版本的执行方向，不替代逐工具审批，不授权新连接器/凭据，不自动变成“总是允许”。

### U2. 审阅卡及三种动作

- 复用现有统一 Intervention 位置与 UI 包，在前后端增加类型化 `plan_review` 等待原因/介入类型。可使用既有 `waiting_input` Run 状态加类型化原因，不要求新增 Run 状态机分支。
- 待审卡位于执行区折叠体外，不能被折叠隐藏；显示 Bot 名、目标、具体版本、阶段列表，超过八项提供“显示全部”。状态由后端投影，不靠 Markdown/工具日志猜测。
- 操作固定为“按这个方案做 / 提出修改 / 拒绝”，无“总是允许”。卡内同时有加载/提交中/错误反馈和版本过期处理。
- **批准**：actor 对所见 planId/reviewRevision 的决定经 CAS 持久化，原 Run 入队恢复；该版本后续真实执行仍按当前资源权限与操作审批检查。
- **提出修改**：需非空具体意见；旧审阅显示“已提出修改”，同 Run 恢复到只制订计划的阶段，生成下一内容版本并重新审阅，不能先执行旧计划或把反馈当新 Task。生成失败/预算不足按现有失败/预算契约如实呈现。
- **拒绝**：原因可选，不强迫填写。原 Run `cancelled`，类型化原因 `plan_rejected`，计划审阅为 rejected；保留 Task/版本/操作者审计。用户看到“已拒绝”，无后续新工具发送，侧栏反映 Bot 其他真实活动而非把整个 Bot 强制改为空闲。
- 提交重复请求幂等；不同页面/旧版本的批准不能批准新版本。版本过期返回业务结果并展示当前审阅卡，不把用户旧点击静默套在新内容上。

### U3. 哪些修订重新审阅

将“内容版本/审批依据”与“执行进度修订”分开，不因每次 Step 或状态事件重新弹审批；可扩展现有版本结构，无需强迫新建第二套计划表。

| 变化 | 行为 |
| --- | --- |
| 目标、阶段内容、阶段增删/顺序/依赖、目标资源或执行范围变化 | 新内容版本，旧批准不覆盖新版本，后续执行前重新审阅 |
| 根据用户“提出修改”生成的新方案 | 新内容版本，必须重新审阅 |
| 当前项、pending/running/done 状态、耗时、尝试/证据/结果、完成后的自然展开收起 | 仅进度修订，不改变已批准的内容依据，不要求重新批准 |
| 完全相同内容的幂等重放，或确定性规范化后相同的无意义格式差异 | 不制造新审阅 |

不让模型自报“这是小改动”决定审批是否失效。批准后发布重要修订，先原子标记新版本待审，再允许后续模型调用/工具阶段前进。已真实发出的外部请求不能伪称撤销或未执行；未发送的下一操作必须检查当前版本授权。

### U4. Todo / Steps 的长期定位

- Plan 是面向用户的目标与阶段，是审批和进度的唯一来源。
- Steps 是实际执行记录、结果和证据；按 planItemId 关联，允许没有 Plan 的合法执行。
- Todo 是 Agent 内部检查清单，保留现有工具/历史模型与兼容能力，不作为第二份用户计划、不参与 Plan 审批、不生成进度分母；新提示词明确职责，不再同时引导模型维护两份“主计划”。
- 关联 Todo/Step 的去重及旧数据 Plan→Steps→事项清单兜底沿用 UX-01。不能为“统一”将三个不同语义的表强行合成一张表，也不能只改页面而保留两套计划批准来源。

## 4. 端到端实施范围

### 后端、契约与持久化

- 实现 planId、内容版本、审批依据、进度修订、draft/pending/approved/changes_requested/rejected 等语义及转换，记录 review actor、时间、反馈、来源。展示 DTO、事件与 snapshot/summary 的字段集中定义。
- 计划发布/更新/提交审阅/决定使用同一个服务与事务边界；schema/API/Worker 按需要正常调整，迁移兼容旧 Run/历史记录。所有入口保留 actor/Space/Thread/generation 与 revision 检查。
- Web action 不直接写计划或外部工具；持久化决定和恢复入队原子/幂等。Clear、Stop、Run 已终态、计划 superseded 时旧卡不能继续执行。
- 计划被拒绝、预算失败、工具审批拒绝是不同事件；不伪造 `approval.resolved=denied` 把计划决定混成工具授权。运行失败时用户能看到真实失败原因。

### Java native Plan Mode 与工具

- 先读锁定 AgentScope 实际输入 schema、权限暂停/恢复和 Plan 状态路径，记录 native→产品计划/审阅的一张映射表，不为此单开 feasibility PR。
- 接通 `plan_enter/plan_write/plan_exit` 与同一个后端计划服务。可以实现明确的 Java facade/bridge 协议或适配原生工具；保留模型可用的规划能力，内容变化落到 PG，而非保留两个互不一致的可执行真相。
- native 工具若要调整输入 schema 为结构化内容，完整修改工具面、校验、提示词和恢复协议，并记录兼容规则；不要在前端从自由 Markdown 推断权威 Plan。
- `publish_run_plan` 等结构化入口与 native 入口互相可见：其中一个发布，另一个读取/修改得到同一 planId 和版本；`plan_exit` 不额外再出一张 `workpal-plan-approval` 泛审批卡。
- 老版本已挂起的 native plan 审批有一次性兼容路径：继续或明确终结原审阅，不丢原 Run、不重复批准或执行；旧执行记录仍可查看。
- 用 AG-05 的每次请求工具刷新表达制订/待审/执行阶段；后端在真实发送前检查版本与当前权限。保留辅助 scope 空工具、helper 停用及已启动后台任务回收。
- 初始/动态/fallback 三条工具 schema 路径均保留 MR-01 的 retryOperationId；计划修订和重试不能造成已完成 operation 重发。

### Web、提示词与恢复

- 统一审阅卡接真实后端状态；和工具审批、ask_input、takeover 共存，各有正确焦点与动作。等待审批时仍可查看执行详情，不能回归 UX-01B 的双入口修复。
- 侧栏继续只用头像徽标、tooltip/aria 表达状态，不恢复状态文字或数字；点击 Bot 定位当前待审卡的首个可操作控件。Task Center 指向同一个审阅和 Run。
- 三层执行展示、唯一 Plan a/b、版本更新提示、失败 Step/Run-level 原因、summary-only/旧 Todo 兜底和 detail retry/rev 竞态保持正确。审批卡外置不等于重复渲染第二份默认计划列表；卡内只显示待决定版本的必要内容。
- 网络断开/刷新/双标签页、Worker/Java 重启、预算后恢复与用户重试均读同一持久状态，不在页面状态中藏唯一批准结果。
- 提示词进 AG-04 根目录及单遍 renderer；说明 Plan/Step/Todo 职责、审阅行为和能力。更新 AG-03 场景/有意 golden 差异，保留独立 trust-rules 字节断言。
- 复用现有 UI 视觉语言、组件和 i18n；新结构字段集中在 API 适配层，不在多个页面散落协议分支。

## 5. 连续开发顺序

一次 preflight/映射与契约 → 统一 PG 服务/typed intervention → native/结构化入口接线及恢复 → 审阅卡/侧栏/Task Center → 兼容、迁移与完整旅程。

这些是同一功能内部提交组；不用为“先后端再前端”“先审阅再修订”“先功能再 E2E”各开 PR。阶段间只跑受影响的本地验证。UI 与真实接口一起交，不接受原型代替完成的链路。
