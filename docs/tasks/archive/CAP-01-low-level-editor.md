## 1. 产品目标与交付方式

在现有 Bot 设置中提供完整的「权限」区域，用户能查看、创建、修改、删除并保存规则，理解冲突时的实际结果，并在真实工具执行中验证设置已经生效。交付包含设计、前端、后端、审计、国际化和端到端验收，一个功能分支、一个 PR、一次最终收口；内部按职责提交，不按页面/API/测试/文档拆 PR。未授权部署。

这不是 JSON 编辑框的包装，也不只是静态设计稿。不得把权限执行放到模型提示词或前端。复用现有 UI 组件与视觉语言，不重做设置系统。

## 2. 已核实的代码事实与产品语义

| 事实 | 权威位置 / 本次约定 |
| --- | --- |
| 规则已经存在 | `Bot.capabilityRules` 为可空 JSON；`packages/contracts/src/capability-rules.ts` 已定义 capability/resource/scope/effect，每 Bot 最多 100 项，capability 最长 128、resource 最长 256 字符。 |
| 没有用户编辑接口 | 当前 `UpdateBotInput` 未包含规则；Web BotSettings 未提供规则编辑。需要补齐 API 和 UI。 |
| 匹配语义 | `packages/core/src/capability-rules.ts`；capability 和 resource 均为不区分大小写的 glob；`*` 不跨 `/`，`**` 可以跨 `/`。不要在前端另写一个匹配器。 |
| 优先级 | 先 deny > ask > allow，再 scope：bot > user > space，再按 capability+resource 字面长度排序。不能靠拖动列表改变优先级；更具体的 allow 不能覆盖 deny。 |
| 内置默认 | read_file / ** / allow；send_email / ** / ask；delete_* / production/** / deny。默认参与同一判定，不是缺少自定义规则时才生效。 |
| allow 不是无审批执行 | executor 的 `requiresApprovalByDefault`、强制审批、无人值守审批和用户审批设置仍生效。UI 使用「允许（遵循其他审批设置）」「每次审批」「禁止」，不要承诺 allow 可以跳过所有审批。 |
| scope 不是全局策略 | 全部规则存于当前 Bot；scope 目前只是该 Bot 内的优先级标签。UI 不提供假的「对整个 Space 生效」开关。新建规则固定 scope=bot；已有其他 scope 可查看、修改 effect/匹配项并保留其 scope，界面解释是历史优先级标签而非跨 Bot 授权。 |
| 资源来源 | `capabilityResourcesForTool` 将可信 connector route.resourceId 与 args.path/resource/resourceId 分开判定，存在多个候选时 deny 优先，其次 ask/allow；显式 production/prod 环境前缀沿用现有语义，不从任意正文猜测生产环境。 |
| 最终权限上限 | capability allow 不增加 Space 成员权、文件权限、凭据或连接器访问，不解除 UX-02 Plan 审批。 |
| 执行时已重读规则 | `packages/adapters/src/capability-permission.ts` 和 executor 在实际调用与批准恢复时重读策略。现有行为保留，不需要为编辑器重建执行引擎。 |

这是对前期「自动允许」「具体规则覆盖默认规则」口头简化的正式纠正。若用户需要真正免审批执行，属于现有审批设置的产品能力，不能通过改 capability allow 的解释偷偷实现。

## 3. 页面与交互任务（前端完整范围）

### F1 — 设计并接入现有设置

- 入口是 `apps/web/src/pages/shell/bot-panel.tsx` 的 BotSettings「权限」区域，独立组件装配；保持现有设置导航/保存习惯，不另造管理后台。
- 先读实际设置布局，使用适用 UI 设计 skill 做同一功能区的布局与交互设计；以实际截图验证默认态、编辑态和错误态。设计在本功能分支内连续落地，不等待单独设计 PR。
- 内容依次为：生效说明、内置默认规则（只读）、此 Bot 的自定义规则、规则试算、保存反馈。用户能识别“已有规则”和“尚未保存草稿”。

### F2 — 规则列表与创建/编辑

- 每条显示操作名称、目标资源、处理方式；可编辑和删除。空列表说明仍沿用内置默认与现有审批流程，不宣称 Bot 无权限或全部自动允许。
- 操作选择来自该 Bot 当前实际工具/连接器可用目录，显示人类可读名称和精确标识；不发明固定「邮件/文件」分类与实际工具的映射。允许在高级输入中填写工具名或 glob，支持当前未连接但已有的规则。
- 资源支持当前可见且已有对应关系的资源选择，以及 glob 高级输入；无法解析的旧 ID 原样显示，不静默改成全部资源。全部资源明确编码为 `**`。
- 新建规则默认 scope=bot，三个 effect 可选。已有规则逐项往返不丢字段；无连接器/目录为空不妨碍配置内置工具或手动模式。
- 内置默认不可删除/改写；可以新增规则，界面展示真实冲突结果，例如添加 allow 后仍被默认 deny 阻止。
- 重复项提示、长度/数量和必填校验在字段旁展示；不做无法依据执行器语义解释的“自动纠错”。

### F3 — 规则试算与生效说明

- 用户选/填一个操作和目标，试算当前草稿，返回「规则允许 / 要求审批 / 禁止 / 无匹配，沿用其他审批设置」及命中来源（内置或自定义）。
- 返回有效参与比较的资源候选与决定依据；同一操作多个资源候选按真实生产判定汇总，不能只展示第一个路径的 allow。
- 试算不调用工具、不读取文件正文、不发连接器请求、不创建 Run/Intervention/ExternalEffect。明确这是能力规则结果，其他权限和审批仍由实际执行检查；没有完整输入时不能承诺最终一定执行。
- 草稿试算与已保存状态清楚区分。试算结果随草稿变更失效，不能继续把旧结果展示为新规则结论。

### F4 — 保存、状态与可访问性

- 编辑为本地草稿；取消/离开未保存区域时沿用设置页已有未保存处理，若原页面没有处理，提供清楚的保存/放弃操作，不静默提交。
- 提供 loading / 无自定义规则 / 读取失败可重试 / 保存中 / 保存失败保留草稿 / 保存成功 / 并发编辑冲突。切 Bot 后不显示或写入上一 Bot 的草稿、晚到请求结果。
- 重新打开以服务端已保存内容为准；其他设置保存不会覆盖此策略，策略保存也不覆盖 Bot 的名称、模型、头像等属性。
- 中文、英文文案齐全；其他语言按仓库已有目录流程处理。键盘可操作、字段与错误关联、弹层焦点/返回焦点、深浅色及现有窄设置面板可用。

## 4. 契约与后端任务（完整范围）

### B1 — 冻结共用契约

- 先以现有 CapabilityRuleSchema 为基础确定读/写/试算 DTO。建议集中为 `bots.capabilityPolicy.get/update/preview`，最终命名一次确定；不把规则塞进每条聊天消息或所有 Bot 列表的大型响应。
- 读取返回 customRules、只读 defaults、并发保存依据和必要展示信息；更新提交完整自定义集合与读取时的保存依据；preview 接收草稿与确定性的操作/资源上下文，返回 matched rule/source 与 decision。
- 并发依据可用规则集合的稳定版本标识，复用现有能力或小幅补充；不要求为此建设通用版本平台。预览所需目录若现有接口够用就复用，不够才补 Bot 范围的最小目录 DTO。
- FE/BE 以这一套 DTO 并行；契约 fixture 可用于前端组件开发，最终必须接真实 API，不把 mock 作为验收。

### B2 — 读取与持久化

- 遵循现有 Bot 设置的 actor/Space/可管理 Bot 授权路径；不能仅凭 botId 读写其他用户或 Space 的策略和资源目录。归档/删除 Bot 的处理与现有设置一致。
- 服务端校验使用原 schema；null/空自定义规则表示使用默认与现有审批流程；禁止把空策略改成新的“默认全允许”。
- 更新原子保存，仅修改目标 Bot 的策略；并发冲突返回明确结果，保留用户草稿并允许重新载入，不静默覆盖他人新设置。
- 沿用现有事件/审计体系记录修改者、目标 Bot、时间、变化前后规则或等价可追溯差异；必要刷新事件与更新一并提交。payload 不包含凭据、原始工具参数或真实文件内容；不另造审计平台。
- 已有非法持久策略读取时明确错误并允许用户主动替换修复；不能读取失败后显示空列表再自动覆盖。已有合法历史 scope、工具名和模式完整保留。

### B3 — 共用判定与试算

- 生产与 preview 共用 `parseCapabilityRules`、resource candidate 提取、`resolveCapabilityRule` 和聚合规则。必要时提取小的纯函数，避免前后端各维护一份默认规则/排序/资源推断。
- preview 只做规则计算；资源目录只返回 actor 已有可见资源，客户端不能通过试算枚举其他用户资源。
- 保存成功后，下一个尚未发送的工具操作及待审批恢复按现行执行时重读规则生效。不取消、撤回或伪称未发生已经发出的外部操作。
- 不修改 allow/ask/deny 既有语义，不绕过行动审批、凭据授权、AG-05 live tool surface、AG-08 撤权、MR-01 操作身份、UX-02 Plan gate。只有本功能引出的具体缺陷才修改相关执行代码并验证。

### B4 — 数据与兼容

- 默认复用已有 Bot.capabilityRules；若采用新增版本字段等必要迁移，在同一功能 PR 完成迁移/旧数据兼容，不拆迁移 PR。
- 不新增 Space/User 全局策略库；不改 scope 的真实含义；不恢复原生 helper。若确实发现任务要求与主干事实冲突，记录事实和影响后集中调整任务，不为每个实现选择停工等待批准。

1. **并发冲突保留草稿不是自动变基。** 原型 `conflictKeep` 只推进 policyRev，没有读入/合并服务器新增规则；生产不得据此声称“已基于最新版”。保留草稿时保持原保存依据，提示需核对最新规则；重新载入可能丢弃草稿的动作需明确确认。要再次保存，先取得最新版并让用户核对整份差异后明确提交，或实现真正合并；不能只换 CAS 标记就覆盖他人变化。不要求建设通用合并平台。
2. **切 Bot 不能静默丢弃未保存输入。** 原型日志里的“已丢弃”不是用户提示。存在未保存草稿时提供保存并继续 / 放弃并继续 / 取消切换；保存失败仍保留原 Bot 和草稿。无草稿正常切换，晚到回包仍隔离。
3. **本功能新增文字使用可读的既有语义令牌。** 不要求复刻既有低对比度的透明度修饰；规则条件、错误和生效说明采用现有可读正文/辅助文字样式，在实际深浅色下检查。全产品旧文字不在此批重做，也不为此另开 UI 优化 PR。

原型本地移植的判定器仅作设计演示；生产仍调用后端 preview，复用 core，不引入第二套前端权限判定。其余 F/B/C-A01–18 完整交付与一次收口约定保持。

## 10. 当前方向：用户动作与操作确认（2026-10-20，替代旧界面契约）

### 10.1 用户纠正与来源

**设计总原则（用户最新明确要求）：** 先从用户要完成的事、已有使用习惯与实际交互出发，参考 Grok 的设计方式；不从数据库字段、规则引擎或假设风险倒推配置页面。付款、邮件、文档只是用户举例，**不构成固定动作分类、页面栏目、功能范围或必须新建的能力清单**。本节后续案例均按此理解。设计者应先识别产品实际存在的用户任务，再决定是否需要设置、是否可在操作当下完成；不得为凑齐配置维度增加表单、复杂草稿或额外确认流程，也不能仅凭官方文档宣称已复刻实际界面。

用户明确要求面向“是否付款、发邮件、操作文档”设计，内部权限与安全机制不向普通用户暴露。旧任务把底层 capability 编辑器当成产品入口，层次选错；只把 tool name 翻译成中文或把配置藏进折叠区仍不满足要求。

查阅的参考为 Grok Bot 官方帮助文档，非实机页面验证：

- [Approvals, security, and privacy](https://docs.x.ai/grok-bot/approvals-security-and-privacy)：在具体操作发生时展示目标和输入，让用户允许一次、保存适用的长期选择或拒绝；设置使用“发外部邮件前先问我”等面向动作的要求。
- [Settings and notifications](https://cursor.com/docs/grok-bot/settings)：个人操作审阅规则位于通用设置，并非要求为每个 Bot 配一份工具表。管理员锁定规则是其另一种产品能力，不能据此推导应该展示 WorkPal 全部内部默认规则。
- [Agent email](https://prod.cursor.com/help/grok-bot/agent-email)：其内置 Bot 邮箱每封都须由用户检查完整草稿再发送，没有免确认发送选项。这是该能力的具体约定，不能把通用 Always allow 推广成所有动作均可绕过确认。

WorkPal 主干已经有 `apps/web/src/components/ApprovalRulesSettings.tsx`、账户设置中的入口、`approvalRules.list/set/remove`、`autoReview.get/set` 和真实 executor 审批路径。应围绕这一现有入口完成用户体验，不再额外建设普通用户可见的 Bot capability 控制台。已有规则和审计数据保留，不能因 UI 改向删掉用户设置或削弱内部约束。

### 10.2 普通用户看到的内容

- 页面名为「操作确认」，放在现有设置入口；用户只需理解动作与自己的选择，例如「发邮件：先让我确认」「付款：先让我确认」「修改文档：按我的要求执行」。这些是交互表达示例，最终展示的动作必须对应产品实际支持的能力，不能凭空新增付款集成。
- 使用用户能理解的三个选择：**按我的要求执行 / 每次确认 / 不允许**。某个动作本来要求用户亲自完成时直接写清，例如“付款确认由你完成”，不提供实际无效的免确认选项。按要求执行不构成对未请求操作的空白授权。
- 阅读、查找、整理和起草与真正发送、付款、修改/删除明确区分。用户要求先确认发送邮件时，不应连查邮件或写草稿都反复打断。文档修改和文档删除的行为需要区分，不能以笼统“操作文档”默认授权删除。
- 对话中的确认卡展示实际动作：邮件收件人、主题与内容；付款对象、金额与币种；文档名称与将进行的变更。用户能够直接确认或拒绝。支持长期选择的动作提供准确的人类可读范围，系统记录匹配关系，不让用户填写工具标识和资源表达式。
- 设置用于查看、修改、移除已经保存的动作偏好。尽量在已有确认流程中形成偏好，不要求用户开工前配置全部选项。
- **删除普通界面中的**内置规则表、工具目录、原始工具名、scope、glob/正则、环境前缀、多资源候选、规则试算、policyRev、规则优先级解释、完整底层差异对比。它们不是“高级模式”保留项；需要调试时使用现有工程证据。
- 安全检查正常在系统内部运行，不把其模型、开关、校验步骤和审计机制变成用户必须理解的设置。真正无法执行时用业务原因解释，不显示解析器/版本术语。

### 10.3 前端与后端实施

**前端：** 在既有操作确认入口连续完成简洁的动作偏好列表、修改/移除、实际确认卡与成功/失败反馈。一个动作的选择就近保存，使用简单的保存中/失败重试；不为本功能建设整份策略草稿、跨 Bot 守卫和复杂变基工作台。复用现有组件、布局和国际化，先交一条真实业务交互，再覆盖其余实际支持动作，不另开原型审批轮。

**后端：** 复用既有审批规则与授权执行路径，补齐用户动作偏好所需的分类、禁止行为和必要业务字段。旧 `always_allow/require_approval` 及 Bot capability 策略不是两套可随意互换的数据：先明确一个用户选择的唯一权威存储和作用范围，再映射执行。旧 Space+用户审批规则保持其作用范围，不擅自扩成跨 Space；Bot 特有限制不被全局动作偏好覆盖。

同一业务动作通过不同路径（例如连接器与浏览器）应遵循同一用户选择；不能仅依据工具名里是否有 email/pay 关键词就宣称业务动作已全面覆盖。沿用当前操作审阅能力并补充实际支持路径的识别与确认；没有可靠覆盖的路径不能显示为“已经全部禁止/允许”。这里不要求建设通用权限平台或自行创造支付能力。

保留服务端鉴权、记录修改、执行时当前配置与必要并发检查；用户只看到“设置有更新，请重新加载后再试”等明确反馈，不需要理解 CAS 或维护整份规则差异。必要的 API/迁移/内部修复随本功能完成，不以复用之名保留错误语义，也不以旧任务为由保留无用后台接口。

### 10.4 #81 的处理与当前验收

继续使用同一个 PR #81，不再按旧18条清单补配置项。可保留真正复用的内部工作；旧编辑器、目录和 preview 服务若无当前产品用途，从本 PR 移除。不要仅为保住已写代码而增加用户流程。

已有评审问题按存活路径处理：跨 Space 导航必须恢复；保留的编辑/保存不能丢输入；保留的动作选择必须实际生效。被撤销的试算界面不再要求修完其独立试算状态机。旧复现测试作为发现证据保留，最终按真实保留行为调整，不把删除整个已撤销功能误报成偷偷删除有效测试。

当前验收以这8项为准：

1. 用户无需了解工具、资源模式、规则优先级即可设置实际支持的发邮件、付款与文档相关偏好；不存在虚构已支持的动作。
2. 查阅/起草与真正发出/付款/改动可区分，确认卡给出用户能够判断的具体内容。
3. 用户选择保存后重开一致，可以修改/移除；失败不谎报保存成功，也不丢失正在输入的选择。
4. 已有用户审批规则和内部约束没有被删掉、放宽或扩大作用范围；新旧设置不形成两套互相矛盾的用户入口。
5. 从页面到实际生产 executor 的受支持动作能验证“按要求执行/每次确认/不允许”的真实结果；确认前无对应外部动作，拒绝后不执行，批准仅执行一次。
6. 同一动作实际支持的 connector/browser 路径一致；不支持/无法识别的路径如实处理，不能只靠 mock 中文标签声称已生效。
7. 跨 Space/Bot 导航、现有设置、Plan 审批、撤权与手动重试不回归；当前保留行为的相关缺陷有定向回归。
8. 新界面实际截图与受影响包检查、必要 API/PG/动作确认 E2E 有完整证据；一次最终功能 PR 收口，保留 roadmap 历史，不部署。
