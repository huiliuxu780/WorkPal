## 用户结果

用户重试一次任务，完成过的同一操作被正确复用，未完成的操作继续执行。两次参数相同的合法操作仍是两次操作。模型跳过、重排已完成动作，不会把另一个动作认成它。未知结果继续使用已批准的确认交互。

## 已核实问题

`manual-retry-match.ts` 的 `occurrenceIndex` 按工具、请求身份和创建时间排序，再用本次执行从零计数的 occurrence 选择旧 effect。这个 ordinal 只描述本次调用顺序，不能跨 Run 表示操作身份。例如原任务有两个相同参数操作，第一个 completed、第二个 uncertain；重试只尝试第二个，它却被记成 occurrence 0，复用第一个结果。已完成提示又会鼓励模型跳过完成动作，因此不能把“模型会按原顺序重新调用”当作前提。

现有 completed-effect fixture 证明了部分复用路径，尚未证明上述跳过/重排语义。PR #64 的相关评审也指出了此问题。不得仅删改 occurrence 断言后宣布修好。

## 实施范围

1. 建立由后端分配、持久化、跨 retry lineage 稳定的 operation identity。明确它与 Run/Attempt/toolCallId/transport nonce 的职责，写出一张生命周期表。
2. 将稳定操作引用提供给重试模型的任务上下文和执行入口。模型引用具体操作，后端检查其链归属、工具、resource/revision、规范化参数及当前授权。模型提供的任意字符串不能自行成为另一任务的操作。
3. 新的独立操作与继续既有操作必须显式区分；同参两次操作不能自动合成一次。参数/目标变化创建新操作；把已有引用绑定到不同参数返回明确业务结果。
4. 整条重试链追踪同一逻辑操作；第三次重试不会因在前一跳产生新的 effect 行而重复执行或拿错旧结果。原 Run 和审计记录保留。
5. 已完成且可恢复结果→复用；真正未执行→按当前权限和审批执行；结果未知→现有三选项确认。用户选择要绑定具体稳定操作并保留原 Task.prompt，不因后续重试被复用到另一操作。
6. 收口任务书验收 11 的预算失败→调整→重试旅程，分别证明单 Run 预算与 Space 预算调整。若当前产品允许预算不足时入队，返回和 UI 就如实显示 queued；不得把未调整原限制而再次失败当作验收成功。
7. 与 AG-04 合流：手动重试固定提示词进入根 `prompts/`、统一单遍 renderer 和生成注册表；删除这次新增的第二套固定提示词目录/loader。插入值含模板标记时原样保留。
8. 完整保留原两个 UI 入口、routine schedule 不变、独立 Worker 领取和执行、合法 nonce 重放、跨用户隔离与副作用审计。

技术方案应实现上述身份契约；不要用“同参就全部跳过”、把所有重试改成手工执行、关闭工具或永久阻断功能替代。若需要协议/迁移，正常实现并覆盖，不因文件数而缩减。
