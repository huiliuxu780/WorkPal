## 需求与结果

现在每次 push 或 PR 更新都会启动完整 CI，任务书、页面组件也跑 Java、模型集成和 Worker 崩溃恢复，同一提交还经常执行两遍。

本任务交付后：文档只做轻量检查，前端跑前端验证，执行链路改动跑对应集成，Worker 改动跑 Worker 链路；同一 PR 更新只有一套 CI。完整验证仍可手动运行，并每日运行一次。

实现包含 workflow 改造、文件范围分类、测试选择、统一结果、真实 GitHub 运行证据和维护说明；不是只增加 path-ignore 或缓存。

## 当前事实

- `.github/workflows/ci.yml` 同时监听所有 `push` 和 `pull_request`，三个 job 都没有文件条件。
- `agentscope` 同时承载 Maven、TS 真实 runtime 集成、PG 旅程、三份 AgentScope E2E 和 Worker 链路。
- `pnpm test:worker-chain` 包含真实约五分钟的租约等待；该验证保留，按范围选择执行。
- `agent-runtime-image` 每次运行都构建 Java 镜像，在 main push 发布 GHCR。它也是需要分类的任务。
- 当前 nightly 是截图 workflow，且引用仓库中未找到的 `playwright.yml`。不能把它当作已有的“每日完整执行链路验证”；本任务建立独立且真实可运行的 full verification 调度，不声称截图问题已修。
- 本次 GitHub branch protection 查询返回未配置保护；实施时重新核实 required checks/rulesets 的实际状态，不自行修改仓库保护设置。

## 触发契约

1. PR 的 opened/synchronize/reopened 等正常代码更新触发一次选择性验证。
2. 普通开发分支 push 不再另起同一套 CI；push 入口只保留 main。保留 PR 的合并上下文测试，不通过取消 PR 测试只留分支测试解决重复。
3. main push 同样按本次实际改动范围验证；文档合并不构建 Java 镜像，不跑 AgentScope/Worker。
4. 增加 workflow_dispatch 的 full 模式，并每日运行 full verification；每天恰有一套完整执行链路，不复用不存在的 screenshot reusable workflow。
5. PR 同一分支有更新时取消过时的一轮；不同 PR 不互相取消。main 和定时/手动完整验证不能被 PR 更新取消。镜像发布仍仅在符合范围的 main push，PR 不发布。
6. 若仓库已有 merge queue/其他触发要求，按真实配置接入；未使用则不新建该流程。

## 文件范围与测试选择

分类基于代码依赖，不凭文件名是否带 agentscope 判断。以下是必须实现的外部行为；具体路径表在检查当前 import、构建上下文和 harness 后落定。

| 修改范围 | 本轮运行 |
| --- | --- |
| 仅 docs/Markdown、不会参与构建的说明文件 | 文档/链接及配置要求内的轻量检查；不安装整套应用依赖、启动数据库或构建镜像 |
| apps/web、ui-web/ui-tokens/chat-ui 等纯 UI | 相关类型检查、Web 单测/build、受影响 focused Web E2E；不因页面改动自动跑 Worker 崩溃恢复 |
| TS adapter、API、提示词、scope/bridge、场景 fixture | 相关 TS checks/单测，以及所影响的 AgentScope 请求集成/PG/E2E；需要 jar 的任务仍先构建 jar |
| services/agent-runtime、Java 依赖、runtime Dockerfile | Maven 与真实 runtime 集成/相关产品 E2E、runtime 镜像；涉及 Worker 执行/恢复的路径同时跑 worker-chain |
| apps/worker、入队/lease/reconcile/outbox/delivery、对应 DB 与 testkit harness | 相关检查/PG 与 worker-chain，连同该链路所需的 jar/构建；不是只跑 Worker 单测 |
| contracts、全局 lockfile/构建设置、跨层 core/db 改动、CI 选择器本身 | 按实际共享依赖展开；影响全局时跑全量。不能把共享契约当成前端专属 |
| prompts/ 下未来 AG-04 的 .md | 作为运行时源码：执行提示词/AgentScope 契约验证，必要镜像构建；绝不能归到“纯文档” |
| 不在已知分类中的源码/构建文件 | 完整验证，并在维护说明列出如何补充准确归属；不能默认零测试 |

改动集合可以命中多类，取任务并集。重命名/删除按受影响的旧、新路径处理。图片/SVG 若属于 runtime/UI 素材，按实际消费者判断，不一律归到 docs。

开发者需要形成仓库可读的路径映射表：路径模式 → 消费者/依赖 → 选中的 job。不要为了少跑而按过窄目录漏掉共享代码，也不要把全部 TypeScript 一概归为全量而使分类无效。

## 实施要求

### 1. 改动计算与选择器

- PR 使用 base/head 的完整 PR 改动范围；main 使用本次 push 的 before/after，而不是只看 HEAD~1。记录实际比较 SHA。
- 在仓库里保留可独立执行的分类脚本或等价的集中式规则，输出明确的 checks 选择结果；路径规则不散落在多个 job 里各维护一份。
- 分类无有效 diff 或读取失败不能直接被解释成纯文档成功；首次分支、全零 before 等 GitHub 实际事件给出明确处理并测试。
- workflow 中显示分类摘要：改动范围、选中/未选中的 job 及原因。用户不需要翻脚本才能知道为什么跑了 AgentScope。

### 2. 拆开执行单元并复用依赖

- 将 agentscope 中 Worker 链路与核心 runtime 验证拆成可按需选择的执行单元；纯 runtime 验证不被迫附带五分钟 lease 测试。
- Java jar 每个执行图只构建所需次数。若 job 间传 artifact，明确上传/下载依赖；选择 worker-chain 时一定有本次提交的 jar，不取 main 旧产物。
- 现有有效命令保留，full 模式包含当前 ci.yml 的全部有效检查。新增 Web 路径验证应包含当前 CI 缺少的 Web 单测与相关 focused E2E，而非只跑 build。
- 使用既有 pnpm/Maven/Docker cache，不把“再引入一套构建系统”当成本任务交付。

### 3. 合并结果与 job 名称

- 提供固定名称的最终结果检查（建议 `CI result`），在选择性、full、docs-only 情况下都出现。
- 结果根据选择清单核对：应该跑的任务必须实际成功；失败、未执行、意外 skipped/cancelled 不能算通过；正确未选中的任务允许不跑。
- 若某个 job 本轮不选中，它依赖的其他 job 不应被误触发，最终结果也不能永远 pending。
- 兼容当前 required checks 的实际配置。若名称迁移确需管理员改设置，在交付中给出准确旧/新名称与操作时机；本 PR 不私自改保护规则。

## 验收标准

1. docs-only PR 一次更新只有一套 CI，没有 Maven、AgentScope、PG、Worker 或镜像构建。
2. 同一 PR push 不再重复出现 push/PR 两组等价检查；取消旧轮只影响同 PR。
3. 前端样例实际运行 Web checks/单测/build 和对应 E2E，Worker 不启动；有跨层依赖的前端改动按并集正确扩展。
4. Java/runtime 样例实际运行所需 Maven/集成/镜像；prompt `.md` 样例不被误分类为 docs。
5. Worker/租约/投递样例实际运行 worker-chain，使用本次提交产物，五分钟恢复断言不缩短或删除。
6. contracts/lockfile/未知源码、重命名/删除、多类同时变更和多提交 main push 的分类结果正确，集中规则有定向测试。
7. 故意让一个已选 job 失败，最终检查失败；正确未选 job 不阻塞；选择器失败不能冒充成功。
8. workflow_dispatch full 在 GitHub 实际跑通当前完整检查集；每日调度指向同一完整执行逻辑，不维护内容不同的两套全量命令。
9. GHCR 发布范围和权限正确；PR 不发布，docs-only main 不发布；不增加任何生产部署动作。
10. 提供优化前/后实际运行数据：docs-only、纯 UI、runtime/Worker 和 full 的 selected jobs、run URL、耗时；无实际执行的类别标注未验证，不能仅凭 YAML 宣称已验证。
11. 无测试 skip、删断言、放宽 timeout 或自动吞掉 flaky 的改动；优化来自选择和去重。
12. 后续新增路径如何分类、如何强制 full、如何读结果都有简明说明。

## 验证与交付

- 本地运行分类规则的定向测试，以及 workflow 语法/结构检查；采用现有可用校验器，不为这项建立新的测试平台。
- 可以通过临时评审分支/PR 证明真实选择结果，避免向 main 提交虚假产品改动；如需额外验证 PR，结束时关闭并在交付中说明。
- 本工作自己的 CI 文件变更应触发 full；不要拿这份 PR 因为改了 workflow 所跑的 full 当作 docs-only 优化无效。
- 交付 `docs/ci01-selective-checks.md`，附原/新 job 图、路径映射、实际 GitHub 证据、耗时和管理员待办（若确有）。
- 任务卡/roadmap 标为 `in-progress / delivered, ready-to-merge`，合入且验收证据齐全后才 done。
- 推送独立 PR，用户审查后合并；本任务不与 AG-03/04 或 MR-01 产品代码混合。
