## Fact freshness (2026-10-18 clarification)

Review finding on PR #50: the contract said stale facts fall back to idle without defining a validity interval, an invalidating event, or a mandatory refetch trigger, so implementations could diverge during a long-running Run or after a missed terminal update. Binding definition:

- **Server (read model).** A state fact is exactly the persisted PostgreSQL state at read time: active Run rows, pending Interventions, running background tasks, failure receipts and `thread.cleared` events. There is **no elapsed-time expiry in the avatar layer** — a legitimately long Run stays `working` for as long as its row is active. A stuck active Run is terminated only by the platform's lease-expiry and reconciler machinery (pinned by the WK-01 acceptance), never by avatar-side guessing. Empty or fully suppressed candidate sets resolve to `idle` through the pinned multi-Run priority.
- **Client (catalog).** A cached state fact is valid **until replaced by a newer successful read** of the avatar catalog. Mandatory refetch triggers: the 2s state poll and the 15s bot-catalog poll (both only while the document is visible), the refresh on visibility resume, and the `workpal:avatar-refresh` event. Polls are serialized — a tick while a request is in flight is skipped — so a late response lands at most one interval late.
- **Failure behavior.** A failed fetch keeps the last confirmed server state; the client never expires it into a locally invented `idle` or `working`. A Bot that was never fetched, or is absent from a successful response, renders as `idle` (unknown → idle).
- **Test boundary.** The PG read-model tests pin the cleared/receipt/priority paths (`packages/db/src/avatar-activity.postgres.test.ts`); the runtime poll tests pin serialization, in-flight skip and visible/hidden behavior (`apps/web/src/lib/avatar-runtime.test.tsx`); the unknown → idle catalog default is pinned in the ui-web component tests.
